# product-content-flow

产品链的前后端闭环：管理端可录、录了能生效、官网产品中心列表与详情显示的是内容本身。详情独立成一条路由 `/product/:slug`，与资讯链彻底分轴。

**本轮（2026-10-31）口径变更**：撤销上一版「产品不做草稿分离、以下架为天然保护态、编辑上架中的产品即时生效」的决定，改为**与资讯链 012 同构的双表模型**——`products` 只放正在上架的行（只读），`product_drafts` 放草稿与已下架（可编辑、可删除）。已上架产品不可编辑、不可删除，唯一动作是下架；下架后可编辑，改完再上架。

## 在全链路中的位置

第 1 步 `site-runtime-link-integrity`（C1，0/64）定好「哪些地址存在、未发布即不可见」之后，本 change 把**产品**这一条链填实。资讯链拆在 `article-content-flow`：本链不含资讯的正文编辑器组件、`article_drafts`、浏览计数去重，也不依赖它们；两链各持自己的表、端点与状态文案常量。与第 2 步 `page-publication-approval`（C2，只管 `pages` 表）无文件冲突；与第 3 步 `decoration-editor-toolkit` 无交集。两条链唯一可能重叠的文件是 `router/index.ts` 与 `public.ts` 的缓存钩子，边界见 design D1/D2 与 D10。

本链的 `010_product_flow.sql` **从未创建也从未执行**，库里 `products` 为 0 行——所以旧口径可以直接原地改写，不需要像资讯链那样另起一个迁移来回避 `011` 的执行记录。

## 规则口径

- **两个目录**：管理端产品（`views/admin/content/product/`）、官网产品中心（`views/website/products/`）；目录内自足（列表 + 编辑/详情 + 分类 + 三个私有编辑器），与资讯的业务实现互不引用
- **详情地址**：两条独立路由，产品 `/product/:slug`、资讯 `/article/:slug`（撤销更早期的 `/option/:type/:slug` 统一形态，C1 已同步修订）；列表页 `/products` 不变；`/products/:slug` 的新旧并存过渡形态与资讯侧同形，其移除归 C1 第 3 组
- **三态与命名**：**草稿 / 已上架 / 已下架**，由服务端常量 `PRODUCT_STATE_TEXT` 单一来源产出 `state_text`；判据不看 `status` 一列，而是「在哪张表 + `product_drafts.state`」——「下架」既是状态也是位置
- **线上只读 + 排序例外**：已上架行的内容列绝对不可写，界面只有「查看 / 下架 / 调整排序」；`sort` 是唯一例外，走只写这一列的专用动作 `POST /products/:id/sort`（否则运营调一次产品中心顺序就要把产品逐个撤下官网）
- **删除只有一种**：作用于未上线表；`DELETE /products/:id` 保留在代码里但界面与文档都不对外使用
- **跨表身份**：`uid` 在两表之间搬运时不变，每个写请求必带 `uid` 做「行 id 与 uid 指向同一行」的校验；审计 `entity_type='product'`、`entity_id=uid`，首次启用 `diff`
- **标识服务端生成且冻结**（2026-11-02 改口径，撤销原「标识可变」）：标识不是运营填的字段，创建落库时生成 `p-{6 位 [a-z0-9]}` 短码（产品分类为 `pc-`），随创建响应下发、界面只读回显；任何写入路径都不接收标识，改名不影响官网地址。唯一性由生成时跨两表占用判定 + 两表 `UNIQUE (slug)` 兜底；存量手工标识不迁移，老地址继续可用
- **形态契约**：`specs` 为 `{label,value}[]`（≤20，行序即展示序）、`gallery` ≤8、`highlights` ≤8；存量 `{}` 由迁移归一为 `[]`，超上限行只统计报告不截断
- **描述富文本**：产品目录私有的 `DescriptionEditor.vue`（Tiptap 3，复用资讯链已装的四个包，不引入新依赖、不抽两条链共用的编辑器基件）；服务端清洗后入库，官网渲染清洗后的 HTML；**描述为空不阻止发布**
- **线索追溯**：下架删线上行会置空 `inquiries.product_id`，故新增 `inquiries.product_uid`，询价按内容身份而不是行主键追溯产品
- **下发与缓存**：`/public/products/:slug` 及其相关推荐补分类名称；产品公开只读接口退出 `max-age`，改 `no-cache` + 内容指纹 ETag
- **三态分层**：装修页未发布 → 整页 404；页面在而列表 0 条 → 列表区空态；请求失败 → 可重试错误态

## 相对上一版新增的三条口径（本轮审计补入）

- **详情所需关联信息由详情一次性下发**：此前详情要显示分类、接口只给 `category_id`，前端恒落到写死的 `'存储产品'`——上一版规划把这条误当成管理端 `GET /products/:id` 的职责，而官网详情走的是 `/public/products/:slug`，两个接口不是一回事
- **公开接口退出 `max-age`**：默认 60 秒的缓存窗口会让「上架即时生效」时快时慢，验收无法判定；改协商缓存后保留 304 复用、内容变更立刻可见
- **双表的代价必须由数据侧兜住**：产品的 `inquiries.product_id` 外键与资讯的 `view_count` 级联是两类代价——资讯可用「重置判重窗口」接受，产品会让线索失去归属，因此必须补 `product_uid`（这是产品链相对资讯链的两处结构差异之一，另一处是产品没有浏览计数）

## 为什么现在必须一起做种子数据

库里 `products` 为 0 行，产品链无法端到端验收，C1 的「产品取 3 条比对」也无从执行。`010_product_flow.sql` 种入 2 个分类与 **4 条产品、四种形态**：① 已上架且字段完整 ② 已上架、仅封面 ③ 草稿 ④ 已下架（带历史上架时间与自定义排序）。②③④ 三行专门用来验证「无数据即不渲染」「草稿经任何公开接口都查不到」「下架后内容仍在、可编辑、再发布后上架时间与排序延续」。与 `011_article_flow.sql`/`012_article_online_readonly.sql` 动的是不同表与不同约束，两者无执行顺序依赖。
