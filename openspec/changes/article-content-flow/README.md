# article-content-flow

资讯链的前后端闭环：富文本撰稿 → **草稿表 / 发布表双表分家** → 公开接口只读发布表 → 官网新闻资讯列表与 `/article/:slug` 详情。未发布内容有自己的存放位置，**线上内容只读、不可删除，唯一动作是下线**；详情独立成一条路由，与产品链彻底分轴。

> **2026-10-30 修订。** 首轮（011 那版）口径是「下线是状态不是位置 + 副本行表示未发布改动」，已全量落地并 94/94 走查。本轮按需求方新口径改写为「一条资讯同时只存在于一张表」，并新增「修改人 + 按内容身份串联的改动记录」。差异与理由集中在 **D10（重写）/ D13、D14（新增）**，落地顺序是 Migration Plan 的**第 10～13 步**（迁移 `012_article_online_readonly.sql`），011 不回改。代码仍停在 011 那版形态，本轮只改纸面。

## 在全链路中的位置

第 1 步 `site-runtime-link-integrity` 定好「哪些地址存在、未发布即不可见」之后，本 change 把**资讯**这一条链填实。产品链拆到 `product-content-flow`：本 change 不含 `products.specs` 的形态收紧与产品上下架端点，产品链也不跟着拆表。与第 2 步 `page-publication-approval`（只管 `pages` 表）无文件冲突——那一边继续用它的 `content_json`/`draft_json` 双列范式，本 change 的双表只作用于资讯，两处「未发布不可见」语义同构、实现不同；与第 3 步 `decoration-editor-toolkit` 只在「编辑器」一词上重名——那一个改装修区块的表单，本 change 的富文本只服务资讯正文，两处不共用实现。

## 规则口径

- 详情地址：**两条独立路由**，资讯 `/article/:slug`、产品 `/product/:slug`（撤销上一版的 `/option/:type/:slug` 统一形态，本轮已同步修订 C1）；列表页 `/news` 不变，旧 `/news/:slug` 移除且不自动跳转
- 路由记录归属：`/article/:slug` 的新增与旧记录移除归 C1 第 3 组，本 change 只改 import 指向与组件实现
- 两个目录：管理端资讯、官网新闻资讯；目录内自足，正文编辑器是管理端资讯目录的私有子件，与产品的业务实现互不引用
- **双表分工**：`articles` = 发布表（**只放正在上线的条目**，`status` 恒为 1），`article_drafts` = 草稿表（从未上线的内容 + 已下线的内容，靠本表 `state` 列区分 0/2）。**一条条目在任一时刻只在其中一张表里**，三形态由「在哪张表 + `state`」唯一确定
- **线上只读**：发布行只有两个动作能写它——发布（新行落表）与下线（整行搬走）。编辑动作拿不到发布行的写入口，界面对在线条目只提供「查看」与「下线」
- **下线是状态也是位置**（本轮推翻 011 那版）：下线在同一个事务内把整行搬回草稿表并置 `state=2`，官网立即不可访问，内容从此可编辑、可删除、可重新发布；`view_count`、`published_at`、`created_*` 随行搬运，不清零
- **不存在「线上 + 副本并存」**：`has_unpublished_changes`、`UNIQUE (published_id)`、「确保副本行」端点、「发布改动」按钮与「放弃改动回到线上内容」一律撤除
- **删除只有一种**：删草稿表的行。`DELETE /articles/:id` 保留在代码里但**不对外使用**（界面不渲染、文档标为运维兜底）
- **每次改动可归人归条**：两表各有 `updated_by`（最后修改人，与 `created_by` 并列，不改对外署名）与 `uid`（跨表稳定身份，两表各唯一）；审计 `audit_logs` 以 `entity_type='article'`、`entity_id=uid` 记录动作与本次改动的字段差异（正文只记长度与摘要），`GET /audit` 支持按 `uid` 精确过滤
- 三个只读接口一律只查发布表，不 join 草稿表——「草稿不可见」由表结构承担，不再依赖每条 SQL 记得写过滤条件
- 状态语义：草稿 / **已上线** / 已下线，全站称谓统一（`ARTICLE_STATE_TEXT` 单点，本轮把「已发布」文案改为「已上线」，键名不动）；新建默认草稿且不写发布时间；`published_at` 只写首次，发布与下线都不重置浏览量与创建信息
- 富文本组件定为 Tiptap 3（4 个包），能力边界由 `backend/src/lib.ts` 的清洗白名单反推：不提供对齐、字号、颜色、缩进、表格；**白名单本身不放宽**
- **非空正文是上下限**：发布与「新建时直接发布」两条路径同样校验，纯空白与 `<p></p>` 一律拒绝
- **正文图片归属**：编辑器只从素材库取图，服务端保存时剥除站外 `img` 并回传数量
- 三态分层：装修页未发布 → 整页 404；页面在而列表 0 条 → 列表区空态；请求失败 → 可重试错误态

## 本轮审计的四个断点与各自的闭合点

- **① 写入落点与读取来源不是同一份** → 由双表闭合（D10）。上一版选的 `articles.draft_json` 差量列被否决：那条「哪一列属于线上」的约定要靠每个读写点自觉遵守，漏一处就把半成品写上线上；双表把约定交给数据库结构本身。本轮更进一步——线上行连编辑入口都没有，写错也写不到线上去。界面侧的验收是 10.2「重开编辑页仍是刚保存的内容」
- **② 分类名与推荐归属在详情与搜索两条下发路径缺失** → D5 补三处 join（详情、相关推荐、`/public/search` 资讯分支），并删除实测的 **5 处** `'NEWS'` 写死兜底（详情 2 处 + 首页两个区块 + 搜索结果 1 处）
- **③ 浏览计数由 GET 触发且被响应缓存吞掉** → D6 显式上报 + 访客窗口判重，D5 让资讯公开接口退出 `max-age`；计数随行搬运，「下线—编辑—再发布」不会清零已累计的浏览
- **④ 引用关系没有级联语义** → D12 给 `article_view_dedupe.article_id` 建 `REFERENCES articles(id) ON DELETE CASCADE`；只加外键不加级联会让「删一篇被人看过的资讯」报 500，都不加则留下指向不存在 id 的孤儿行。本轮下线本身就是"移除线上行"，级联因此在每一次下线时都会清空该条的判重明细（见取舍第三条）

## 三条已定的取舍口径

- **id 选择规则**：读写内容按草稿表行 id（新建、改草稿、发布、删除），线上侧只剩下线按发布表行 id。发布之所以走草稿 id：首次发布时发布行还不存在，走草稿 id 能让首次与再发布共用一个端点。管理列表一行只回传**一个 id + 来源标记 `origin`**，写请求再带上 `uid` 让服务端校验「这个 id 确实是这条内容」——两表主键各自递增，数字相同不代表同一条内容
- **改线上内容必须先下线**：代价是官网在「下线 → 改完 → 再发布」这段时间该条不可访问，界面在下线确认里点名这一后果。被否决的替代是「留一份待发布副本、改完再覆盖」，那正是 011 那版的形态，本轮按需求方要求撤销
- **下线会重置 24 小时判重窗口**：级联清理浏览明细是"删线上行"的既成后果，同一访客在重新上线后可再计一次。本 change 接受这条有界偏差——浏览量是展示口径，不是审计口径；改动历史按 `uid` 聚合在 `audit_logs`，不受影响

## 为什么现在必须一起做种子数据

执行迁移前库里 `articles` 只有 1 条手工遗留行，没有覆盖各形态的样例，资讯链无法端到端验收，C1 的「资讯取 3 条比对」也无从执行。011 建 `article_drafts` 与带级联的 `article_view_dedupe`、把 `status=0` 的存量行搬出发布表并将 `CHECK` 收窄为 `(1,2)`，并种入 2 个分类与 4 条内容；本轮的 `012_article_online_readonly.sql` 在此基础上把 `status=2` 的行回收进草稿表、降级旧副本行、`DROP COLUMN published_id`、把 `CHECK` 收到只允许 1，并重排为**三形态样例**（已上线两条供倒序与分页、草稿一条、**已下线一条且带非零浏览量与历史发布时间**，专门验收「下线后内容仍在、可编辑、可重新发布且计数延续」）。种入的正文只使用能力边界内的标签，因此种子行本身就是「编辑器产出 = 清洗后保留 = 官网渲染」三者一致的回归样本。与 `010_product_flow.sql` 无执行顺序依赖。
