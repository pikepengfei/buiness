依赖：本 change 建立在两份**已交付**的 change 之上——`component-library-standalone`（真实渲染卡片 `LibraryCard` / `LibraryGrid`、右侧抽屉、三栏结构、`demo` 透传）与 `decoration-editor-toolkit`（模板库标签页、拖拽与批量、`LibraryCard` 的可选 `blocks`）。渲染器（`SectionRenderer`）、注册表、插入判据、上限护栏全部沿用，本 change **只替换预览的承载方式**，不动区块数据模型与插入链路。

## 现状盘点

- 官网样式全站只有一个真正生效的入口：`src/layout/WebsiteLayout.vue:212` 的**非 scoped** `<style>`。另外 4 处 `@import url('@/assets/website.css')` 全写在 `<style scoped>` 里（`editor.vue:951`、`LibraryCard.vue:78`、`components.vue:419`、`Preview.vue:48`），被 Vite 内联后又被 Vue 加上 `data-v`，对子组件渲染出的区块**一条都不匹配**
- 实测：编辑页样式表里命中 `.hero` 的规则 20 条，全部带 scoped 属性，不带属性的 0 条
- 编辑器右栏是「1280px 定宽画布 + `transform: scale(0.5~1)`」（`editor.vue:855` 与 `.ed-canvas`），媒体查询按后台窗口宽度判定
- 组件库卡片：模块 `scale(0.32)` + 定宽 1240px、基础元素原比例且**不挂官网作用域类**（`LibraryCard.vue:57`）；组件库页详情弹窗另有一套 `fitScale × zoom` + `ResizeObserver` 测量（`components.vue:138`）
- 官网样式自身：35,623 字节，**零 `url()`、零 `@font-face`、零 `@import`**，断点为 `max-width: 1100 / 860 / 640 / 480`；变量定义在 `:root`
- 区块组件的样式分两类：官网全局样式（大部分）+ 自身 scoped 样式（21 个模块中 8 个有、3 个基础元素全有）。注册表是**静态 import**，所以这些 scoped 样式在编辑页加载时就已注入宿主 head
- 全局环境：`App.vue:26` 的非 scoped `<style>` 引入 `assets/style/main.css`（含后台 reset），官网与后台**本来就共用**这一份全局层叠环境
- 单测环境是 happy-dom（`vitest.config.ts:9`），不保证 iframe 文档与跨文档节点移动的行为

## 实测证据（本机浏览器，2026-11-12）

在运行中的编辑页里做了一次性探针（探针建临时 iframe、测完即移除，未改动任何项目代码）：

| 探针 | 结果 |
| --- | --- |
| 复制宿主 78 张样式表（内联约 397KB）+ 追加官网样式 35.6KB | 构建耗时 **50ms** |
| 把**宿主创建**的节点移入 iframe 文档 | 节点立即按 iframe 文档的样式表计算（Teleport 的底层机制成立） |
| iframe 宽 1280px | 首屏内边距 96px、背景 `rgb(248,245,240)`、容器 1240px、正文 `"Source Han Sans SC"` / 行高 25.6px / 色 `rgb(22,22,22)`、主标题 54px/800、品牌色 `#DE6420` |
| 同一 iframe 改成 500px | `max-width: 640px` 命中、首屏内边距 64px、主标题 34px/800 |
| 再改回 1280px | 桌面数值完整恢复（切换幂等、无需重建） |
| 后台自身 | 按钮内边距仍 `5px 16px`、正文字体仍 `PingFangSC`；同页旧画布里的首屏内边距仍 **0px**（现状缺陷的同页对照） |
| 跨文档共享 constructed stylesheet | **被浏览器拒绝**：`NotAllowedError: Sharing constructed stylesheets in multiple documents is not allowed` |

结论：同源 iframe + 复制宿主样式表 + 官网样式置末 + Teleport 注入，能在**不改动官网样式一行**的前提下拿到逐项一致，且响应式按 iframe 宽度真实判定。

## Goals / Non-Goals

**Goals:**

- 组件库效果与编辑器实时预览与官网**逐项一致**（版式/间距/字体/颜色/尺寸/交互态/响应式/内容）
- 响应式按**所选设备视口**判定，与后台窗口宽度解耦
- 草稿变更即时同步，且反复操作幂等、无累积
- 后台与预览**双向隔离**：互不改写对方的呈现
- 实时预览带真实官网外壳，运营看得到模块的页面上下文

**Non-Goals:**

- 不改 `src/assets/website.css` 与全局 tokens（项目硬约束），不改区块组件的视觉实现
- 不改区块数据模型、插入判据、上限护栏、保存与发布链路；零后端改动
- 不做预览内的「点选区块定位到结构树」（属编辑器交互增强，另议）
- 不做预览截图导出、不做多设备并排对比视图
- 不引入新 npm 依赖（含 e2e 框架）
- 不做后台自身的移动端适配

## Decisions

### D1 隔离宿主用同源 iframe，不用 Shadow DOM、不改官网样式

预览内容放进一个同源 `iframe` 的文档里渲染。iframe 自带独立的 `:root`、`body`、视口与媒体查询环境，官网样式里的 `:root` 变量、`body` 字体、`* { box-sizing }`、`@media` 全部原样成立——**这是唯一不改官网样式就能拿到完全一致环境的容器**。同源是必须的：只有同源才能直接操作其文档、移入节点、复制样式表。

否决的替代方案：

- **把 `@import` 从 scoped 移到非 scoped**（最小改动）：官网样式含 `body`、`*`、`a`、`img`、`button` 等裸元素选择器，一旦全局生效会改写整个后台的字体、链接与图片表现；且媒体查询仍按后台窗口判定，响应式缺陷不解决
- **Shadow DOM 隔离**：官网样式的 `:root` 变量与 `body` 字体在 shadow 树内不匹配，`@media` 仍按主窗口宽度；要适配必须重写官网样式，违反「不改 website.css」硬约束
- **容器查询重写官网样式**（把 `@media` 换成 `@container`）：等于改造官网本体，风险外溢到 5 个线上页面；且 `vh`/`vw` 与 `body` 字体仍无法容器化
- **维持现状、逐个组件补样式**：21 个模块 + 4 个基础元素各补一份「预览专用样式」，等于维护第二套官网皮肤，必然漂移

### D2 一个 Vue 应用 + Teleport 注入，不给每个 iframe 起第二个应用

宿主组件在自己的文档里正常渲染官网区块，再用 Vue 的 `Teleport` 把渲染结果指向 iframe 文档内的挂载点。Teleport 底层是 DOM 插入，浏览器会自动把节点**收养**进目标文档（实测成立），于是节点按 iframe 的样式表计算，而组件仍属于**同一个应用实例**——router、pinia、响应式、scoped `data-v` 标识全部不变，草稿一改预览立即更新，不需要序列化、不需要跨文档通信。

否决的替代方案：

- **每个 iframe 内 `createApp` 独立挂载**：组件库一屏 20+ 卡片就是 20+ 个应用实例，各自重复 router/pinia；草稿同步要手动把 props 序列化传进去，「即时同步、状态一致」两条都变脆
- **iframe 直接加载 `/preview/:slug` 真实路由**：那是第二个 SPA 实例（重复登录态与请求），且草稿还在内存里没保存，跨文档同步要靠 `postMessage` 传整棵树，每次按键都可能重挂载
- **`srcdoc` 写整页 HTML**：近 400KB 样式要塞进属性字符串，转义与体积都不可接受，且更新等于整页重载
- **`document.adoptNode` 手工搬运**：等于手写 Teleport，还要自己处理卸载与更新时序，没有收益

### D3 样式环境 = 复制宿主全部样式表 + 官网样式原文置末

构建宿主文档时：写入 `<!doctype html>` 与 `<base href="/">`（保证 `/uploads/...` 与相对资源按站点根解析）→ 按宿主 `document.styleSheets` 的**原顺序**复制每个 `<style>` 的文本与每个 `<link>` 节点 → **最后**追加官网样式原文（以 `?raw` 引入，类型由 `src/vite-env.d.ts` 的 `vite/client` 提供）→ 建根容器并挂官网作用域类。

为什么复制**全部**而不是挑「官网相关」：官网与后台本来就是同一个 SPA、共用 `App.vue` 的全局层叠环境，官网样式的最终计算值是「全局 reset + Element Plus 按需样式 + 官网样式置末」共同作用的结果。复制全集并保持顺序，才是复现官网而不是近似官网；后台专有的 scoped 规则带的是后台组件的 `data-v`，在预览节点上不匹配，后台的 ID 前缀规则（`#app …`）在 iframe 里没有 `#app` 也不匹配——实测后台与预览双向不串味。

否决的替代方案：

- **只注入官网样式**：丢掉全局 reset 与 Element Plus 按需样式，得到的是「官网样式 - 全局环境」的第三种呈现，仍不一致
- **按选择器前缀挑子集**：需要维护一份「哪些算官网样式」的清单，随组件增减漂移，且 Element Plus 按需样式的加载时机不可预测
- **跨文档共享 constructed stylesheet**（`adoptedStyleSheets`，本想用来省掉重复解析）：**本机浏览器直接抛 `NotAllowedError`**，规范不允许跨文档共享，方案作废
- **`<link>` 指向构建产物 CSS**：dev 环境没有产物文件，且官网样式在 dev 是内联 `<style>`，两种环境行为会分叉

### D4 宿主 head 增量镜像，而不是一次性快照

宿主文档建好后，用 `MutationObserver` 监听宿主 `document.head` 的新增/移除样式节点与文本变化，把增量按序镜像进每个存活的预览文档，并始终保持官网样式在**最后一位**。理由：Element Plus 按需样式与 HMR 都可能在宿主建好之后才注入/替换样式；只拍一次快照会在这些时机丢样式。注册表是静态 import，所以区块自身的 scoped 样式在编辑页加载时已就位，增量镜像是兜底而非主路径。

否决的替代方案：

- **一次性快照**：HMR 改一处样式后预览与官网立刻分叉，开发期最难排查的一类「预览又不一样了」
- **定时轮询样式表数量**：有延迟、有空转，且拿不到「内容被替换」这类变化
- **每次草稿变更都重建宿主文档**：50ms × 每次按键，且会闪白、丢失滚动位置与交互态

### D5 设备视口 = iframe 宽度，缩放只作用于外壳

设备预设取 **桌面 1440 / 平板 834 / 手机 390**（可调常量）：官网断点是 1100 / 860 / 640 / 480，1440 落在全部断点之上、834 落在 860 与 640 之间、390 落在 480 之下——三档正好把官网的三种版式都覆盖到。iframe 的 CSS 宽度**等于设备宽度**，媒体查询与 `vh`/`vw` 因此真实成立（实测 1280 → 500 → 1280 切换即生效且可逆）。显示倍率通过对外层容器 `transform: scale()` 实现，外层尺寸按 `设备宽度 × 倍率` 同步，**倍率不参与版式判定**。倍率默认按预览区可见宽度自动适配，并允许手动覆盖，界面标明当前设备与倍率。

否决的替代方案：

- **维持 1280px 定宽画布 + scale**（现状）：媒体查询按后台窗口判定，窄窗口下桌面预览显示移动版式，这是本次要修的缺陷之一
- **CSS `zoom`**：各浏览器对 `zoom` 与媒体查询/`vh` 的交互不一致，且缩放后仍需容器宽度真实等于设备宽度才有意义
- **把断点改成容器查询**：见 D1，等于改造官网本体

### D6 官网外壳靠 Layout 插槽复用，不另抄一份

`WebsiteLayout.vue` 的内容区从固定 `<router-view />` 改为「默认插槽 + 回落 `<router-view />`」。预览把区块作为插槽内容传进去，于是导航、页脚、站点配置（品牌色、Logo、导航项）全部走**同一份实现与同一份数据**。官网前台不传插槽，渲染结果零变化。

否决的替代方案：

- **在预览里抄一份导航与页脚模板**：站点设置改了预览不改，正是「状态不一致」的新来源
- **iframe 里加载真实官网路由**：见 D2，第二个 SPA 实例 + 跨文档草稿同步
- **不要外壳**：运营看不到首屏模块在导航之下的真实位置与留白，本 change 的上下文诉求落空

### D7 交互隔离：捕获阶段拦截导航，卡片屏蔽指针事件

实时预览要**保留**交互态（悬停/聚焦），所以不能盖遮罩。改为在预览文档上以**捕获阶段**监听点击与提交，对链接与提交调用 `preventDefault()`——vue-router 的链接守卫尊重 `defaultPrevented`，因此拦截即不跳转，同时给出「预览内不跳转」的即时反馈。组件库卡片是「点一下就插入」的语境，预览区整体 `pointer-events: none`，点击统一落到外层卡片的插入动作。

否决的替代方案：

- **给每个区块组件加 `preview` 分支禁用链接**：要改 21 个模块 + 4 个基础元素，且「预览里的组件」与「官网的组件」实现分叉，与保真目标相反
- **iframe `sandbox`**：同源能力被削掉，样式复制与节点注入都做不了
- **实时预览也盖透明遮罩**：连悬停一起吃掉，交互态就不一致了（卡片可以，实时预览不行）
- **只拦 `click` 不拦 `submit`**：联系表单类模块在预览里可能真提交，产生脏线索数据

### D8 高度与滚动：实时预览定高内部滚动，卡片自动高度后缩放裁切

实时预览：iframe 高度 = 预览区可见高度 ÷ 倍率，内容在 iframe **内部滚动**。这样 `vh` 与首屏高度按真实设备视口成立，且滚动条属于预览而非后台。组件库卡片：iframe 先按设备宽度自动高度渲染，测量内容高度后按倍率换算卡片内的占位尺寸并裁切到定高，保证列表滚动条稳定、卡片不跳。

否决的替代方案：

- **卡片沿用固定 170px 硬裁**（现状）：高模块只露一条边，看不出效果；自动高度测量后裁切能按倍率给出稳定占位
- **实时预览也用自动高度、由后台滚动**：`vh` 失去意义（文档高度等于内容高度），首屏模块的高度判定会与官网不同
- **两者都内部滚动**：卡片里出现 20+ 个可滚动区域，滚轮归属混乱

### D9 卡片懒挂载 + 保活上限，超出即释放

沿用 `IntersectionObserver` 懒挂载（进入可视区才建宿主），但把原来的「触发后永久保活」改为**保活上限**（默认 8，常量可调）：超出上限时释放最久未可见的宿主，再次可见时重建。理由：一个宿主的样式环境实测约 400KB 文本 / 50ms 构建，组件库 20+ 项全量保活会到 8MB 量级文本与几十个文档；重建走缓存后的样式文本，成本可控且结果幂等。抽屉关闭时释放全部宿主。

否决的替代方案：

- **全量保活**（现状口径）：几十个文档常驻，内存与首屏开销不可控
- **虚拟滚动**：库总量级（<40 项）用不上，且卡片高度不一会让滚动跳跃
- **整个列表共用一个宿主**：卡片与外壳的对齐要手工换算，滚动/裁切/点击归属全部变复杂，收益不抵风险

### D10 测试接缝：纯函数单测 + 宿主打桩 + 浏览器实测清单

把可判定逻辑收进 `previewFrame.ts` 的纯函数（样式收集顺序与官网样式置末、设备预设、倍率与占位尺寸换算、缓存签名、释放幂等），这部分直接单测。组件单测对宿主**打桩**（happy-dom 不保证 iframe 文档与跨文档节点移动），断言「传入的设备宽度/倍率/内容」与「就绪/失败态」，既有 DOM 契约与断言口径不放宽。真正的「逐项一致」由浏览器实测清单承担：同一视口下对照官网与预览的计算样式与几何量，逐项记录。

否决的替代方案：

- **在 happy-dom 里断言计算样式**：happy-dom 不做完整层叠与媒体查询，断言通过也不代表一致，属假绿
- **引入 Playwright 做 e2e**：新增依赖，违反「不轻易新增 npm 依赖」；本次保真判据用浏览器实测 + 计算样式对照即可覆盖
- **只靠人工肉眼比对**：字体、行高、内边距这类差异肉眼容易放过，必须留数值判据

### D11 失效导入清理与官网样式入口收敛

删掉 4 处写在 scoped 里的官网样式导入（编辑器、组件库卡片、组件库页、草稿预览页）。草稿预览页本就在 Layout 内、拿的是真正生效的非 scoped 样式，删掉死代码后渲染结果不变。收敛后官网样式只有两个入口：**Layout 的非 scoped `<style>`**（官网与草稿预览页）与**预览宿主的原文注入**（后台内的所有预览）。在 `docs/前端执行文档.md` 写死这条硬约束，避免以后又有人往 scoped 里 `@import` 官网样式。

否决的替代方案：**留着「反正不生效也无害」**——它会让下一个读代码的人以为预览样式已经引入，正是这次缺陷能长期存在的原因。

### D12 与已交付 change 的顺序与契约保持

本 change 排在 `component-library-standalone` 与 `decoration-editor-toolkit` **之后**，只替换预览承载：卡片的 `.lib-cell` / `.lib-label` / `.lib-type` / `.lib-reason` / `data-lib-type` 与 `pick` 事件、抽屉的 tabs 结构、插入判据与上限护栏、模板面板复用卡片的可选内容入口，全部保持不变。模板缩略因此自动获得同样的保真度，无需改动模板面板。

否决的替代方案：**顺手重构组件库面板结构**——会与刚交付的抽屉/模板库单测正面冲突，且与保真目标无关。

## 三态口径（内容可见性）

| 状态 | 实时预览（后台） | 组件库效果 | 官网前台 |

## 性能预算

- 单个宿主样式环境构建 ≤ 80ms（实测 50ms / 78 张表）；样式文本按宿主样式表签名做模块级缓存，同签名不重复取文本
- 组件库同时保活宿主 ≤ 8；抽屉关闭即全部释放
- 实时预览宿主常驻 1 个；切换设备/倍率**不重建文档**，只改宽度与外层尺寸
- 草稿变更到预览更新在同一帧的响应式更新内完成，不做防抖延迟（输入即所见）

## 迁移与回滚

无数据变更：**零迁移、零接口、零 schema 改动**，因此无迁移脚本与反向回滚脚本。回滚 = 前端 `git revert` 本 change 的提交；`WebsiteLayout.vue` 的插槽为回落式改动，回滚后官网前台立即恢复原状。

## 风险与缓解

- **后台全局样式含裸元素选择器时会进入预览**：但它同样作用于今天的官网（同一个 SPA），因此**保真性由构造保证**；实施时抽查后台非 scoped 样式，若发现只应作用于后台的裸选择器，另开变更收敛，不在本 change 里改全局样式
- **iframe 内资源路径**：`<base href="/">` + 同源保证 `/uploads/...` 与站内相对路径成立；实测官网样式零 `url()`，无字体/背景图相对路径风险
- **Teleport 目标就绪时序**：宿主文档就绪后才渲染内容，未就绪显示占位；失败显示不可用提示 + 重试（对应 spec 的失败场景）
- **happy-dom 与真实浏览器行为差异**：靠 D10 的接缝切分与浏览器实测清单兜住，不在单测里断言计算样式
