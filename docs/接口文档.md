## 1. 基础约定

### 1.1 服务地址

| 项 | 值 | 来源 |
|---|---|---|
| Base URL | `http://<host>:<port>` | `PORT`（默认 3000） |
| API 前缀 | `/api` | `API_PREFIX` |
| 健康检查 | `GET /health` | 无鉴权，返回 `{ ok, ts }` |

下文所有路径均以 `/api` 为前缀，例如登录接口完整路径为 `POST /api/auth/login`。

### 1.2 认证方式

- 受保护接口需在请求头携带访问令牌：`Authorization: Bearer <accessToken>`
- 令牌为 JWT，`accessToken` 默认有效期 `2h`（`ACCESS_TOKEN_TTL`），`refreshToken` 默认 `14d`（`REFRESH_TOKEN_TTL`）。
- 公开接口（`/api/public/*`、`/api/auth/login`、`/api/auth/refresh`、`/api/auth/logout`、`/api/forms/*`）无需令牌。
- 权限接口按 RBAC 权限点校验，详见 [附录 A](#附录-a-权限点对照)。

#### 刷新令牌轮换（Token Rotation）
`POST /api/auth/refresh` 采用一次性轮换：每次刷新会**吊销旧 refreshToken 会话**，并同时下发**全新的 accessToken 与 refreshToken**。客户端必须用返回的新 `refreshToken` 覆盖本地存储的旧值；若使用已轮换的旧 refreshToken 再次刷新，将返回 `401`（`code=2006`）。

#### 口令传输约定

所有口令字段（`password` / `oldPassword` / `newPassword`）都不传明文：浏览器内先算 `sha256(明文)`，
提交 64 位小写十六进制摘要（前端 `src/utils/password.ts` 的 `passwordDigest`，与后端
`createHash('sha256')` 结果一致）。服务端不解密、也拿不到明文，仍按原逻辑对该摘要做加盐
bcrypt（cost=12）后入库。

- 摘要本身即登录凭证，接口必须部署在 HTTPS 下；口令长度与复杂度只能在前端表单校验。
- 服务端脚本需按同一口径生成哈希：`bcrypt(sha256Hex(明文))`，`scripts/setup-admin.ts` 已内置。
- 切换前落库的 `bcrypt(明文)` 账号无法再登录，需重置口令（`ADMIN_PASSWORD_RESET=1 npm run setup-admin`）。

### 1.3 统一响应结构

所有接口返回 JSON，结构一致：

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "meta": { "page": 1, "pageSize": 10, "total": 42 }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | number | `0` 表示成功；非 0 为业务错误码（见 [附录 B](#附录-b-业务错误码表)） |
| `message` | string | 描述信息；成功为 `ok`，失败为可读错误原因 |
| `data` | any | 业务数据载荷；无数据时为 `null` |
| `meta` | object | 仅分页接口返回，含 `page / pageSize / total`；个别接口在 `meta` 追加字段（如媒体库列表的 `categories`） |

> 说明：HTTP 状态码表达传输语义（400/401/403/404/409/429/500），业务错误码 `code` 表达细粒度业务含义，前端应**优先按 `code` 分支处理**。

#### 全局错误处理

路由抛出的异常（非接口显式 `send` 的错误）由 `app.ts` 中的全局错误处理器统一兜底。处理器现注册于业务路由之前，已真正生效（此前注册顺序有误，先注册的路由仍走 Fastify 默认序列化）：

| 异常来源 | HTTP | code | message |
|---|---|---|---|
| Fastify schema 校验失败 | 400 | 1001 | `请求参数校验失败` |
| zod `.parse()` 抛出的 `ZodError` | 400 | 1001 | 仅回传**首个问题**：`参数不合法：<字段路径> <原因>` |
| 数据库唯一冲突（SQLSTATE 23505） | 409 | 3002 | `记录已存在（唯一字段冲突）` |
| 数据库外键冲突（SQLSTATE 23503） | 400 | 1004 | `关联记录不存在，请检查所选分类等关联项` |
| 其余异常 | 按状态 | — | 按 HTTP 状态映射业务码（`400→1001`、`401→2001`、`403→2005`、`404→3001`、`409→3002`、`422→1003`、其他→`9001`） |

未注册路由统一返回 `404/3001`，message 含 `方法 + 路径`。

### 1.4 限流

全局启用 `@fastify/rate-limit`，默认 `300` 次 / `60s`（`RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW`，`.env` 与 `.env.example` 默认值同为 300；`config.ts` 内置兜底亦为 300）。超限返回 HTTP `429`。

全局默认值已从早期版本的 `20` 次/分钟提高到 `300` 次/分钟：管理后台为单页应用，一个页面加载即并发发起多组列表/字典请求，过小阈值会误伤正常操作。防滥用不再依赖全局阈值，改由需要严格限流的具体路由以路由级 `config.rateLimit` 单独收紧（覆盖全局默认值）：

| 路由 | 单独限额 | 目的 |
|---|---|---|
| `POST /api/auth/login` | 10 次 / 分钟 | 防暴力破解 |
| `POST /api/forms/:kind`（inquiry / cooperation / contact） | 10 次 / 分钟 | 公开表单防滥用 |
| `POST /api/forms/subscription` | 10 次 / 分钟 | 公开订阅防刷 |

### 1.5 缓存

`/api/public/*` 只读接口默认附带响应头（`PUBLIC_CACHE_MAX_AGE`，默认 60 秒；`<=0` 禁用）：

```
Cache-Control: public, max-age=60, s-maxage=60, stale-while-revalidate=30
```

例外：内容类公开只读接口要求「后台上架/下架/发布/下线即时生效」，改用协商缓存——`/public/pages/:slug`、`/public/products`、`/public/products/:slug`、`/public/product-categories`、`/public/articles`、`/public/articles/:slug`、`/public/article-categories`、`/public/search`。两者都是 `Cache-Control: no-cache` + `ETag` + 命中 `If-None-Match` 回 `304`，指纹来源不同：

- 单页 `/public/pages/:slug` 用行身份与时间戳 `"pg{id}-{updated_at 毫秒}"`（发布与草稿保存都会刷新 `updated_at`）；
- 产品与资讯的列表/详情/分类及 `/public/search` 走 `negotiateCache`，ETag 是**响应内容的 md5 指纹**并按接口分组加前缀：`prod-list`/`prod-one`/`prod-cat`、`art-list`/`art-one`/`art-cat`、`search`；内容一变指纹即变，不依赖时间列是否被刷新，因此「上架一条产品」「下架后再上架」下一跳就能在官网看到；
- 上述 max-age 头由 onSend 钩子统一附加，且仅在处理器未显式设定 `cache-control` 时生效，因此其余公开接口（`/public/site`、`/public/banners`、`/public/faqs` 等）仍走 max-age 短缓存。

## 2. 鉴权 Auth

### 2.1 登录

`POST /api/auth/login` · 鉴权：公开

请求体：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `username` | string | 是 | 2–50 |
| `password` | string | 是 | 口令 SHA-256 摘要，`/^[0-9a-f]{64}$/` |

成功响应 `data`：

```json
{
  "accessToken": "eyJ...",
  "refreshToken": "eyJ...",
  "user": {
    "id": 1, "username": "admin", "displayName": "超级管理员",
    "roleId": 1, "roleCode": "super_admin", "permissions": ["*"]
  }
}
```

失败：`401/1003`（用户名或密码错误）、`403/2004`（账号被禁用）。登录成功/失败均写入 `login_logs`。

### 2.2 刷新令牌（轮换）

`POST /api/auth/refresh` · 鉴权：公开

请求体：`{ "refreshToken": "eyJ..." }`（≥10 字符）

成功响应 `data`：`{ "accessToken": "新AT", "refreshToken": "新RT" }`

失败：`401/2002`（刷新令牌无效）、`401/2006`（会话已失效，需重新登录）。

### 2.3 退出登录

`POST /api/auth/logout` · 鉴权：公开

请求体：`{ "refreshToken": "eyJ..." }`。删除对应会话；无论令牌是否存在均返回成功（幂等）。

### 2.4 当前用户信息

`GET /api/auth/me` · 鉴权：需登录

成功响应 `data`：`{ id, username, displayName, roleId, roleCode, permissions }`

### 2.5 修改密码

`POST /api/auth/change-password` · 鉴权：需登录

请求体：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `oldPassword` | string | 是 | 原口令 SHA-256 摘要（64 位小写十六进制） |
| `newPassword` | string | 是 | 新口令 SHA-256 摘要（64 位小写十六进制） |

成功：`data=null`。**副作用**：改密成功后吊销该用户全部刷新会话（强制其他设备重新登录）。
失败：`401/2007`（原密码错误）。

### 2.6 更新当前用户资料

`PATCH /api/auth/me` · 鉴权：需登录

请求体（均可选，至少一项）：

| 字段 | 类型 | 约束 |
|---|---|---|
| `displayName` | string | 1–50 |
| `email` | string | 邮箱或空串 |
| `avatarUrl` | string | URL 或空串 |

成功响应 `data`：更新后的用户信息（结构同 2.4）。无字段返回 `400/1002`。

## 3. 用户与角色 Users

> 除 `/roles` 外均需 `user:write` 权限。

### 3.1 角色列表

`GET /api/roles` · 鉴权：需登录

`data`：`[{ id, code, name, description, permissions }]`

### 3.2 用户列表（分页）

`GET /api/users` · 权限：`user:write`

查询参数：`page`（默认 1）、`pageSize`（默认 10，上限 100）、`keyword`（模糊匹配用户名/邮箱/显示名，ILIKE 已做通配符转义）、`status`（0/1 精确）、`roleId`（正整数精确）

`data` 行字段：`id, username, email, display_name, avatar_url, role_id, role_name, status, last_login_at, created_at`；`meta` 含总数。

### 3.3 新建用户

`POST /api/users` · 权限：`user:write`

请求体：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `username` | string | 是 | 2–50，唯一 |
| `password` | string | 是 | 口令 SHA-256 摘要（64 位），服务端 bcrypt 后入库 |
| `displayName` | string | 是 | 1–50 |
| `roleId` | number | 是 | 正整数 |
| `email` | string | 否 | 邮箱或空串 |
| `avatarUrl` | string | 否 | URL 或空串 |

成功：`data={ id }`。用户名重复返回 `409/1003`（message 提示"用户名已存在"）。

### 3.4 用户详情 / 更新 / 删除

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/users/:id` | 返回单用户（不含密码字段）；不存在 `404/3001` |
| PATCH | `/api/users/:id` | 可改 `displayName/email/roleId/status/password/avatarUrl`；传 `password`（口令 SHA-256 摘要）将重置 |
| DELETE | `/api/users/:id` | 删除用户；不可删除自身（`400`） |

`PATCH` 请求体字段均可选：`displayName`(1–50)、`email`、`roleId`(正整数)、`status`(0/1)、`password`(口令 SHA-256 摘要，64 位)。

## 4. 内容管理 CMS

> 读接口需 `content:read`，写接口需 `content:write`。所有 `:id` 路径参数须为正整数，否则 `400/1001`。
> 写操作均写入 `audit_logs`。富文本字段（`articles.body`、`faqs.answer`、`pages.content_json` 字符串叶子）入库前经 XSS 清洗。
> 批量排序：Banner / FAQ / 菜单 / 产品分类 / 资讯分类均提供 `POST /api/<资源>/reorder`（见各小节表格）。请求体 `{ items: [{ id, sort }] }`（1–500 项，`id` 正整数、`sort` 0–999999），后端单事务逐条写入，审计动作 `reorder`，返回 `data={ updated }`。

### 4.1 单页 Pages（区块化装修 · 草稿/发布双版本）

页面内容以「区块数组」存储，`content_json` 为线上正式版本、`draft_json` 为管理端草稿版本，结构均为 `{ blocks: [{ id, type, visible, props }] }`（详见《数据结构文档》区块规范）。官网公开接口仅返回 `status=1` 的 `content_json`，草稿不外泄。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/pages` | 列表（精简列，含 `has_unpublished_draft` 计算字段） |
| POST | `/api/pages` | 新建（`content_json` 与 `draft_json` 同初始化；slug 冲突 `409/3002`） |
| GET | `/api/pages/by-slug/:slug` | 按 slug 取整页（含 `draft_json`），编辑器使用 |
| GET | `/api/pages/:id` | 详情（含 `draft_json`） |
| PATCH | `/api/pages/:id` | 仅更新 meta（`title/metaTitle/metaDescription/heroImage`） |
| PUT | `/api/pages/:id/draft` | 保存草稿（body `{ contentJson }`，结构校验见下，`deepSanitize` 清洗，不影响线上） |
| DELETE | `/api/pages/:id/draft` | 放弃草稿：`draft_json` 复位为 `{}`，编辑器回落线上版本（审计动作 `discard_draft`；页面不存在 `404/3001`） |
| POST | `/api/pages/:id/publish` | 发布：单条 UPDATE 原子完成 `content_json=draft_json`、`status=1`、`published_at=COALESCE(...)`；草稿从未保存（`draft_json` 无 `blocks` 数组）时返回 `400/1001`，保护线上内容不被清空 |
| POST | `/api/pages/:id/unpublish` | 下线：`status=0`（公开接口不再返回该页） |
| DELETE | `/api/pages/:id` | 删除 |

`POST` 请求体：`slug`(1–80,必填)、`title`(1–120,必填)、`metaTitle`(≤160)、`metaDescription`(≤300)、`heroImage`、`status`(0/1，默认0)、`contentJson`(默认`{}`)。
`GET /api/pages` 返回行字段：`id/slug/title/status/published_at/has_unpublished_draft/updated_at`；`has_unpublished_draft` = `draft_json` 非空且与 `content_json` 不同。
`PUT /api/pages/:id/draft` 请求体：`{ "contentJson": { "blocks": [...] } }`。
> `contentJson` 结构校验（`POST /api/pages` 与 `PUT /api/pages/:id/draft` 共用，实现见 `backend/src/blocks.ts`）：区块节点递归同构——`{ id, type, visible, props, children? }`，`children` 是同一结构的数组（模块装载的基础元素子树）。`id` 1–64 字符、`type` 1–40 字符、`visible` 布尔（默认 `true`）、`props` 对象（默认 `{}`）；具体 `type` 与 `props` 内容由前端 sectionRegistry 定义，后端不校验类型清单。
> 上限（与前端 `src/website/blocks.ts` 的 `BLOCK_LIMITS` 同值，两侧需同步）：页面顶层区块 ≤ **200**、单模块 `children` ≤ **50**、嵌套深度 ≤ **4**（顶层为 1）、单页节点总数 ≤ **400**。深度与总数 zod 表达不了，由 `blockLimitIssues` 遍历复核。
> 不合规返回 `400/1001`，`message` 带出错位置：zod 侧给出字段路径（如 `blocks.0.children.0.type`），上限侧给出「位置 + 原因」（如 `blocks.0.children.0.children.0.children.0.children.0：嵌套深度超过 4 层`）。`children` 子树内的字符串叶子同样经 `deepSanitize` 递归清洗后入库（`draft_json = jsonb(deepSanitize(校验通过的树))`）。
> 无 `content:write` 权限提交结构变更返回 `403`，草稿不落库；前端编辑器的部署护栏（渲染器结构版本 < 2 时禁止保存带 `children` 的内容）在调本接口前拦截。
> 区块内容的编辑闭环：编辑器 `by-slug` 取草稿 → 修改 → `PUT draft` 保存（官网不变）→ `POST publish` 发布（官网即时生效）。

### 4.2 资讯分类 Article Categories

| 方法 | 路径 | 请求体 |
|---|---|---|
| GET | `/api/article-categories` | — |
| POST | `/api/article-categories` | `name`(必填)、`description`、`sort`(默认0)；**不收 `slug`**，服务端生成 `ac-{6 位}` 后返回 `{ id, slug }` |
| PATCH | `/api/article-categories/:id` | `name/description/sort` 部分字段；**`slug` 不可写**（提交即被丢弃），一个可写字段都没带时 `400`「无更新字段」 |
| DELETE | `/api/article-categories/:id` | 被引用时 `409`，`message` 给出「线上 X 条、草稿 Y 条」的占用数量 |
| POST | `/api/article-categories/reorder` | 批量排序（约定见第 4 节引言） |

`GET` 每行带 `ref_count`：**跨 `articles` 与 `article_drafts` 两张表**统计，与删除前置检查同一来源（只统计线上表会让「仅草稿在用」的分类显示 0 条却被拒）。分类的 `slug` 由服务端在创建时生成（`ac-` + 6 位 `[a-z0-9]`，生成前查本表占用），此后冻结、无任何写入路径，因此不再有「分类标识冲突」这类人工输入错误；两个不同分类拿到同一个码只可能是并发争抢，由 `article_categories_slug_key` 兜住并转 `409`。

### 4.3 资讯 Articles（双表：线上只读 + 未上线可编辑）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/articles` | 列表：`articles` 与 `article_drafts` 的 `UNION ALL` 并集，一行一条内容，回传 `origin`/`state`/`state_text`/`uid`/`updated_by_name` |
| GET | `/api/articles/:id` | 线上行详情（只读形态） |
| GET | `/api/articles/drafts/:draftId` | 未上线行详情（编辑所需完整字段） |
| POST | `/api/articles/drafts` | 新建未上线内容（只落 `article_drafts`，`state=0`）；请求体**不收 `slug`/`status`/`state`**，收到即被丢弃；**标识在这一刻生成**并随 `INSERT` 同笔写入；返回 `{ id, uid, slug, stripped_images }` |
| PATCH | `/api/articles/drafts/:draftId` | 更新，请求体必带 `uid`；可写列见下表（**不含 `slug`**）；返回 `{ stripped_images }` |
| DELETE | `/api/articles/drafts/:draftId` | 删除，`uid` 走查询参数 |
| POST | `/api/articles/drafts/:draftId/publish` | 发布 = 事务内整行搬进 `articles`，`uid` 与 `slug` 原样带过去；`body` 非空下限在这里第二次把关 |
| POST | `/api/articles/:id/unpublish` | 下线 = 事务内整行搬回 `article_drafts` 并置 `state=2`（`view_count`、`published_at`、`created_*` 随行） |
| DELETE | `/api/articles/:id` | **运维兜底，界面与文档不对外使用**（正常流程不产生需要删除的线上行） |

六个写端点统一挂 `content:write`，读取挂 `content:read`。

**请求体字段**（`POST /articles/drafts` 全量，`PATCH` 为 `partial()` 并额外必带 `uid`；camelCase，落库列名为 snake_case）：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `slug` | — | **不收** | 由服务端在创建落库时生成 `a-{6 位 [a-z0-9]}`（跨 `articles` + `article_drafts` 判占用），此后任何写入路径都不可改；提交值被 zod 丢弃且不报错 |
| `title` | string | 是 | 1–200；不合规返回 `400`「参数错误：标题必填，且各字段长度受限」 |
| `coverImage` `summary` `author` | string | 否 | 500 / 400 / 50；用 `nullish`：传 `null`=清空、不传=不动 |
| `body` | string | 否 | 创建可缺省；入库前 `sanitize` + 站外图片剥除，剥除数量随 `stripped_images` 回传；**发布时非空下限生效**（空串、纯空白、只有空标签都拒） |

**错误与并发口径**（与产品侧同构，文案见 §4.5 对应行）：`409` 有四种来源——发布时线上已有同 `slug` 行、下线时草稿表已有同 `slug` 行（都只在存量手工标识之间才可能发生）、同一 `uid` 重复搬运、行 id 与 `uid` 不符；正文空下限为 `400`；`PATCH` 未带任何可更新列为 `400`「无更新字段」；两表 `UNIQUE(uid)`、`UNIQUE(slug)` 兜并发，PG 的 `23505` 统一转 `409` 而不是 500。审计与三态判据同产品侧（`entity_type='article'`、`entity_id=uid`、`ARTICLE_STATE_TEXT`）。

> 资讯的双表契约由 `article-content-flow` 交付（迁移 011→012）；三态判据与产品同构（见 §4.5 末尾），称谓为「草稿 / 已上线 / 已下线」。

### 4.5 产品 Products（双表：已上架只读 + 未上架可编辑）

**错误与并发口径**：

| 情形 | 响应 |
|---|---|
| 上架时线上已有同 `slug` 行 | `409` 「标识「x」与线上产品冲突，请先修改未上架内容的标识」——**只可能发生在存量手工标识之间**：新建的标识由服务端生成且不落已占用值，没有人工输入口 |
| 下架时未上架表已有同 `slug` 行 | `409` 「标识「x」已被一条未上架产品占用，下架会产生同标识的未上架行，请先处理该产品」（同上，仅存量数据触发） |
| 生成的标识在重试上限内每次都撞上已占用值 | 该次 `INSERT` 撞 `products_slug_key` / `product_drafts_slug_key` → `409`「记录已存在（唯一字段冲突）」`code=3002`；**不静默改名**、不落未经占用判定的值 |
| 同一 `uid` 重复搬运（并发双发布/双下架） | `409` 「该内容身份已有线上行，重复搬运会被拒绝」/「该内容身份已有未上架行，无法再次搬运」；两表 `UNIQUE(uid)`、`UNIQUE(slug)` 兜底，PG 的 `23505` 统一转 `409` 而不是 500 |
| 路径行 id 与提交的 `uid` 不是同一条内容 | `409` 「行 id 与内容身份不符：未上架表第 N 行不是你提交的这条产品，请求已拒绝」（线上行同形文案）——服务端不按 id 猜测 |
| `PATCH` 未带任何可更新列 | `400` 「无更新字段」 |
| 形态越界（`specs` 非数组/21 项/缺 `label`、`gallery` 9 项、`highlights` 9 条） | `400`，给出首个越界字段 |
| 未登录 / 只有 `content:read` 却调用写操作 | `401` / `403`（六个写端点统一挂 `content:write`） |

**三态判据与文案单点**：`origin='online'` → 已上架；`origin='draft'` 且 `state=0` → 草稿；`origin='draft'` 且 `state=2` → 已下架。文案来自服务端常量 `PRODUCT_STATE_TEXT`，随列表行的 `state_text` 与错误提示下发，前端不另维护称谓映射（资讯侧同构常量为 `ARTICLE_STATE_TEXT`：已上线/已下线）。

**审计留痕**：六个写路径各记一条 `audit_logs`，`entity_type='product'`、`entity_id=` **`uid`**（行 id 会随搬运消失）、`action ∈ create/update/delete/publish/unpublish/sort`、`diff={fields, from, to}`。`fields` 只收值真的变了（整份表单回写时未动的列不进审计）；`description` 只记 `{length, summary}`；`publish`/`unpublish` 记 `state` 的变化（`草稿 → 已上架` 等）。读取按 `GET /api/audit?entityType=product&entityUid=`（见 §4.11）。

### 4.11 审计日志 Audit

`GET /api/audit` · 权限：`content:read` · 分页（按创建时间倒序，`meta` 含 `page / pageSize / total`）

查询参数：`page`/`pageSize`、`entityType`（精确）、`action`（精确）、`entityUid`（精确，需合法 UUID 形态，否则 `400` 「entityUid 需为合法的标识格式」）、`keyword`（模糊匹配实体 ID / IP / 操作人用户名，ILIKE 已做通配符转义）。

`data` 行：`id, user_id, action, entity_type, entity_id, diff, ip, created_at`，并 JOIN `users` 附带 `username`（操作人）

**`entity_id` 存的是内容身份 `uid`，不是行 id。** 产品与资讯的发布/下架会把整行在两张表之间搬运，行 id 每次换表都变；只有 `uid` 能串起一条内容的完整时间线，所以 `entityUid=` 是取全链路的唯一正确参数（`GET /api/audit?entityType=product&entityUid=<uid>`），`keyword` 搜行 id 搜不到跨表历史。

`diff` 形状固定为 `{fields, from, to}`：正文/富文本类字段（`body`、`description`）不存原文，只存 `{length, summary}` 摘要；发布与下架动作记 `state` 的变化（`草稿 → 已上架` 等）。`fields` 的收录口径两链不同——产品侧只收值真的变了（或本次真的提交）的列，整份表单回写时未动的列不进审计；资讯侧仍记录本次提交的全部列，这是登记在案的不对称，不是本文件写错。

| GET | `/api/leads/stats` | lead:read | 三张线索表按状态计数汇总 |

`inquiry` 的列表行额外带派生字段 `product`：按 `product_uid` 跨 `products` + `product_drafts` 回查这条产品的**当前**指向，形如 `{ name, slug, origin, state_text }`（线上行优先，回落未上架行；`state_text` 取产品三态常量，下架期间给到「已下架」而不是空指向）；本页没有带产品身份的线索时该键为 `null`，字段向后兼容（只新增，不改既有字段名）。该字段只在接口层下发，管理端线索列表页目前尚未渲染这一列。
`PATCH` 请求体（至少一项）：`status`、`note`、`handledBy`。`:id` 非法返回 `400`。

`GET /api/leads/stats` 响应 `data` 示例：

```json
{
  "inquiries": { "0": 12, "1": 3, "2": 1, "3": 0 },
  "cooperation": { "0": 5 },
  "contact_messages": { "0": 8, "1": 2 }
}
```

## 6. 上传 Upload

> 均需 `media:write` 权限。生产推荐“预签名直传”（文件不经后端）。

### 6.1 预签名上传地址

`POST /api/upload/presign`

请求体：`filename`(必填)、`contentType`(默认 application/octet-stream)、`category`(默认general)。

响应 `data`：

```json
{
  "objectKey": "general/202610/uuid.webp",
  "uploadUrl": "https://...（600s 有效预签名 PUT）",
  "url": "https://cdn.example.com/website/general/202610/uuid.webp",
  "method": "PUT"
}
```

流程：拿 `uploadUrl` 后浏览器以 `PUT` 直传对象存储；上传完成后调 `POST /api/media` 登记。
本地存储模式（`STORAGE_DRIVER=local`）不支持预签名，`uploadUrl` 为空、`method=POST`，需走 6.2。

### 6.2 服务端直传（仅本地模式）

`POST /api/upload/direct` · `multipart/form-data`

查询参数：`category`(默认general)。云端模式下调用以 `400/5002` 提示改用预签名。未收到文件 `400/5001`。
响应 `data`：`{ id, url, objectKey }`（自动写入 media 记录）。

### 6.3 官网 Logo（固定命名）

`POST /api/upload/logo` · `multipart/form-data`

字段 `file` 必填，图片校验口径同 6.2（扩展名白名单 → 声明 MIME → 文件头签名）。
对象键固定为 `brand/logo.<ext>`：同名覆盖，换扩展名（png → webp）时清除上一版文件；本地与云端存储模式都支持（由后端落盘 / PutObject）。

**不写入 media 素材库**：素材允许删除并清除物理文件，而引用扫描不覆盖 `site_settings`，Logo 一旦进了素材库，一次误删就会让官网顶栏 404。

成功后直接把访问地址写回站点设置 `logo_url`，响应 `data`：`{ url, objectKey }`，前端无需再调 `PATCH /api/settings`。
`url` 形如 `/uploads/brand/logo.png?v=1793154563211` —— 对象名固定而内容会变，`?v=` 用于穿透浏览器与 CDN 缓存。

## 7. 公开只读接口 Public

> 无需鉴权；默认附带 max-age 短缓存头（见 1.5；例外：7.7 单页走 `no-cache` + ETag 协商缓存）。适用于官网前台。

### 7.1 站点配置 + 导航

`GET /api/public/site`

`data`：`{ settings: { general:{...}, seo:{...}, social:{...}, contact:{...} }, menus: [树] }`

### 7.2 Banner

`GET /api/public/banners?position=home`（默认 home）
仅返回启用且在时间窗口内的 Banner。`data` 行：`id, title, image_url, link_url, position`。

### 7.3 产品列表（公开）

`GET /api/public/products`

| 参数 | 说明 |
|---|---|
| `page` / `pageSize` | 分页 |
| `category` | 分类筛选：纯数字按分类 ID，其余按分类 slug 解析（子查询取对应分类 id） |
| `keyword` | 名称/系列模糊（ILIKE，通配符转义，三元组索引加速） |
| `sort` | `price` 按价格文本，否则按 sort |

`data` 行：`id, slug, name, series, cover_image, summary, price_text, category`；`meta` 含总数。

### 7.4 产品详情

`GET /api/public/products/:slug`
返回上架产品全字段 + `related`（同分类其他产品，最多 4 条）；不存在时 `data=null`。

### 7.5 产品分类 / 资讯分类

`GET /api/public/product-categories` 、 `GET /api/public/article-categories`：按 sort 返回全部分类。

> 分类行的 `slug` 同时是 §7.3/§7.6 `category` 筛选参数的取值。内容域的标识改为服务端生成的不透明短码后，新建分类的筛选地址形如 `?category=pc-4t7kq2`；解析规则不变（非数字即按 `slug` 子查询取分类 id），对不上任何分类时返回空列表而不是报错。存量分类的标识未迁移，老筛选地址继续有效。

### 7.6 资讯列表 / 详情（公开）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/public/articles?category=&page=&pageSize=` | 仅已发布；行含 `id,slug,title,cover_image,summary,tags,author,published_at,category` |
| GET | `/api/public/articles/:slug` | 详情 + `related`（同分类最多4条）；**自增 `view_count`** |

`category` 参数与 7.3 一致：数字按分类 ID、其余按分类 slug 解析（此前仅按数字解析，传 slug 会失败，现已统一）。

### 7.7 单页

`GET /api/public/pages/:slug`：返回已发布单页（含 `content_json`）；不存在 `data=null`。
缓存策略区别于其他公开接口（要求发布即时生效，见 1.5）：响应头 `Cache-Control: no-cache` + `ETag`（形如 `"pg{id}-{updated_at 毫秒}"`）；请求携带 `If-None-Match` 且与当前 ETag 一致时返回 `304`。

### 7.8 FAQ

`GET /api/public/faqs?category=`：返回启用 FAQ；`data` 行：`id, question, answer, category`。

### 7.9 全站搜索

`GET /api/public/search?q=关键词`

- `q` 为空返回空结果；`q` 超过 100 字符返回 `400/1001`。
- 输入中的 `%`/`_`/`\` 会被转义，避免被当作匹配模式。
- `data`：`{ products: [...最多20], articles: [...最多20] }`。

## 附录 C：分页与排序约定

- 分页参数：`page`（从 1 起，最小 1）、`pageSize`（默认 10，上限 100）；`meta.total` 为符合条件的总行数。
- 列表总数采用单次往返窗口函数（`COUNT(*) OVER()`）计算，避免两次查询。
- 默认排序：产品按 `sort, created_at DESC`；资讯按 `published_at DESC NULLS LAST, created_at DESC`；媒体/审计按 `created_at DESC`。

## 附录 D：数据结构速查

字段与 JSONB 结构约定详见《数据结构文档.md》。关键点：

- 主键统一 `BIGSERIAL`；对外使用 `slug`/`object_key` 等不可枚举标识。
- 状态枚举：`articles.status` / `products.status` 恒 1（`CHECK (status = 1)`，线上表只放正在上架的内容），未上线侧由 `article_drafts.state` / `product_drafts.state` 取 0/2（草稿 / 已下线·已下架，`CHECK (state IN (0,2))`）；展示类(0/1)、线索(0/1/2/3)，关键表已加 CHECK 约束。
- JSONB：`products.specs` `[{label,value}]`、`products.highlights` `[]`、`products.gallery` `[object_key]`、`articles.tags` `[]`、`pages.content_json` / `pages.draft_json` `{ blocks: [{id,type,visible,props}] }`、`roles.permissions` `["*"] 或 ["..."]`。
