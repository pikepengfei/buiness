# 数据结构文档 · Centremix 芯联创企业官网

> 配套脚本：`z-buiness/backend/sql/schema.sql`（PostgreSQL 14+）
> 本文档描述云端数据库的逻辑结构，供前端、后端与运维共同遵循。

## 1. 总体实体关系（ERD 概览）

```
roles 1──< users 1──< user_sessions
                  │
                  ├──< articles   >── article_categories
                  ├──< products   >── product_categories
                  ├──< pages
                  ├──< media
                  ├──< inquiries  ── products
                  ├──< cooperation
                  ├──< contact_messages
                  └──< audit_logs

site_settings (KV)   menus (树)   banners   faqs   subscriptions (独立)
```

- **核心内容实体**：`products` / `articles` / `pages` / `banners` / `faqs`，均由 `users` 创建并写入 `audit_logs`。
- **线索实体**：`inquiries` / `cooperation` / `contact_messages` 来自前台表单，统一含 `status` 状态机，可关联 `handled_by`（运营）。
- **配置实体**：`site_settings`（KV）、`menus`（树）、`roles`（RBAC）。

## 2. 表结构明细

### 2.1 用户与权限
| 表 | 关键字段 | 说明 |
|---|---|---|
| `roles` | code(PK 唯一), name, permissions(JSONB) | RBAC 角色，permissions 为权限点数组；`super_admin` 含 `["*"]` |
| `users` | username, email, password_hash(bcrypt), role_id→roles, status, last_login_* | 后台账号；status=1 启用 |
| `user_sessions` | user_id, refresh_token_hash, expires_at, ip, user_agent | 刷新令牌仅存哈希 |
| `login_logs` | user_id, ip, user_agent, success, reason | 登录审计，含失败原因 |

### 2.2 站点配置与导航
| 表 | 关键字段 | 说明 |
|---|---|---|
| `site_settings` | key(PK 唯一), value, group_name, label | 全局 KV；group 分 general/seo/social/contact |
| `menus` | parent_id(自引用), title, url, target, sort, status | 多级导航；首页/关于/产品/资讯/售后由种子写入 |

### 2.3 内容管理
| 表 | 关键字段 | 说明 |
|---|---|---|
| `pages` | slug(唯一), title, meta_*, hero_image, status, content_json(JSONB), draft_json(JSONB), published_at | 可编辑单页；`content_json` 线上正式版本、`draft_json` 管理端草稿版本，均为区块化结构 `{ blocks:[...] }`（见 §5.1）。迁移 `002_page_blocks.sql` 新增 `draft_json` 并写入 home/about/products/news/contact 种子；迁移 `003_list_blocks.sql` 在 products/news 页插入 `product-grid`/`news-feed`/`poster-grid`/`cta-banner` 区块 |
| `article_categories` | name, slug(唯一) | 资讯分类 |
| `articles` | slug, title, cover_image, body(HTML), category_id, tags(JSONB), status, published_at, view_count | 资讯/文章；status:0草稿/1发布/2下线；含全文检索 GIN 索引 |
| `product_categories` | name, slug, parent_id(自引用) | 产品分类（多级） |
| `products` | slug, name, category_id, series, cover_image, gallery(JSONB), summary, description, specs(JSONB), highlights(JSONB), price_text, buy_link, status, sort | 产品主表；gallery/specs/highlights 均为 JSONB |
| `banners` | title, image_url, link_url, position, sort, status, start_at, end_at | 广告位，按 position 区分页面 |
| `faqs` | question, answer, category, sort, status | 售后/保修/退换 FAQ |
| `media` | filename, original_name, mime_type, size, bucket, object_key, url, category | 媒体库，记录云端对象键与访问 URL。支持改名（`original_name`）/归类（`category`）但**不改动访问 `url`**（避免已发布内容失效）；删除前会跨 `pages`/`products`/`articles`/`banners` 扫描 `object_key` 引用，被引用时拒绝删除 |

### 2.4 表单与线索

### 2.5 审计
| 表 | 关键字段 | 说明 |
|---|---|---|
| `audit_logs` | user_id, action, entity_type, entity_id, diff(JSONB), ip | 操作留痕（create/update/delete/publish） |

## 5. JSONB 字段结构约定

- **products.specs**：`[{"label":"容量","value":"20TB"}, ...]`
- **products.highlights**：`["原厂直供","稳定供应", ...]`
- **products.gallery**：`["media/xxx.webp","media/yyy.webp"]`（object_key 数组）
- **articles.tags**：`["贸易合规","市场洞察"]`
- **pages.content_json / draft_json**：整页区块化结构，见下方 §5.1 区块规范
- **roles.permissions**：`["content:read","content:write"]` 或 `["*"]`

### 5.1 pages 区块（blocks）规范

页面内容 = 有序区块列表，`content_json` 与 `draft_json` 结构一致：

```jsonc
{
  "blocks": [
    {
      "id": "home-hero",        // 区块实例 id（编辑器新增时前端 genBlockId 生成，type+随机短串）
      "type": "hero",            // 区块类型，对应前端 sectionRegistry
      "visible": true,           // 显隐开关（false 时前台/预览跳过渲染）
      "props": { /* 各类型专属内容数据：文案/图片/列表项 */ }  // 仅内容，不含样式结构
    }
  ]
}
```

- **草稿/线上双版本 + 发布覆盖的数据流**：
  - 管理端编辑器「保存草稿」→ `PUT /pages/:id/draft` 仅写 `draft_json`（经 `deepSanitize` 递归清洗），`content_json` 不变，官网前台不受影响。
  - 「发布」→ `POST /pages/:id/publish` 执行 `content_json = draft_json, status = 1, published_at = COALESCE(published_at, NOW())`；草稿为空（`draft_json.blocks` 非数组）时后端拒绝发布，避免覆盖成空内容。
  - 「放弃草稿」→ `DELETE /pages/:id/draft` 将 `draft_json` 复位为 `{}`，编辑器回落线上版本。
  - 「下线」→ `POST /pages/:id/unpublish` 置 `status=0`，公开接口按 `status=1` 过滤后不再返回该页。
  - 前台 `GET /public/pages/:slug` 只读 `status=1` 的 `content_json`，草稿不外泄。
- **has_unpublished_draft**（`GET /pages` 列表即时计算，不落库）：`(draft_json <> '{}'::jsonb AND draft_json IS DISTINCT FROM content_json)`，即草稿已结构化且与线上不同才提示「有未发布修改」。
- **迁移 `003_list_blocks.sql`（本轮已执行）**：不再重写整页，而是以 JSONB 切片在**指定区块（`page-hero`，第 1 块）之后插入**新区块——products 页插入 `product-grid`，news 页依次插入 `news-feed` → `poster-grid` → `cta-banner`。幂等条件：仅当 `content_json::text` 不含该区块 type（如 `NOT LIKE '%"product-grid"%'`）才插入，重复执行不产生重复区块、也不改动管理端已编辑的其余区块与顺序；当草稿也已结构化（`draft_json ? 'blocks'` 且不含该 type）时，`draft_json` 同步插入同一份新区块。
- **19 种区块类型**（type 与关键 props，与前端 `sectionRegistry.ts` 的 `defaultProps`、`pageDefaults.ts` 兜底、迁移种子三方一致）：

- **各导航页默认区块（种子，含 002 + 003）**：
  - home：hero → intro-eco → mvv → values → feature-products → story → pm-entry → latest-news → cta-banner
  - about：page-hero → intro-eco → timeline → story(含 brandWall) → cta-banner
  - products：page-hero → **product-grid** → cat-grid → cap-flow → cta-banner（产品列表由 product-grid 区块承载）
  - news：page-hero → **news-feed** → **poster-grid** → **cta-banner**（资讯列表由 news-feed 区块承载）
  - contact：page-hero → cat-grid → timeline → faq-list → contact-form → cta-banner
- **兼容说明**：旧写法 `[...]` 已废弃；解析器 `parseBlocks` 仅接受 `{ blocks: [...] }` 对象形式，字符串会自动 JSON.parse。

## 6. 索引与性能

- 所有 `slug` 字段唯一索引，作为公开路由标识（不可枚举性优于自增 ID）。
- `articles` / `products` 建立 `to_tsvector` GIN 索引支撑全站搜索。
- 列表查询按 `status + (published_at|sort)` 复合索引；外键列建索引。
- 大表（articles/products/audit_logs）按 `created_at` 分区可后期演进（单表千万级内无需）。

## 7. 安全与合规要点

- `password_hash` 存 `bcrypt(口令 SHA-256 摘要)`（cost=12）：前端只提交摘要，明文密码既不进接口也不落库。摘要即登录凭证，故接口必须走 HTTPS。
- `refresh_token` 仅存哈希，原始令牌签发后即弃。
- 富文本（articles.body / pages.content_json / faqs.answer）入库前须做 XSS 清洗（后端 sanitize）。
- `audit_logs` 对所有写操作留痕，满足 CMS-06 审核流需求。
- 个人信息（inquiries/contact 的 phone/email）按隐私政策最小化收集，并提供导出/删除接口（合规预留）。
