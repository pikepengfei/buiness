# 数据结构文档 · Centremix 芯联创企业官网

> 配套脚本：`z-buiness/backend/sql/schema.sql`（PostgreSQL 14+）
> 本文档描述云端数据库的逻辑结构，供前端、后端与运维共同遵循。

## 1. 总体实体关系（ERD 概览）

```
roles 1──< users 1──< user_sessions
                  │
                  ├──< articles   >── article_categories   ←→  article_drafts（未上线内容）
                  ├──< products   >── product_categories   ←→  product_drafts（未上架内容）
                  ├──< pages
                  ├──< media
                  ├──< inquiries  ── products（+ product_uid 跨表追溯）
                  ├──< cooperation
                  ├──< contact_messages
                  └──< audit_logs

site_settings (KV)   menus (树)   banners   faqs   subscriptions (独立)
```

- **核心内容实体**：`products` / `articles` / `pages` / `banners` / `faqs`，均由 `users` 创建并写入 `audit_logs`。
- **内容表成对出现**：`articles`/`products` 是**线上表**，只放正在对外可见的行且**只读**；`article_drafts`/`product_drafts` 是**未上线表**，承载草稿与已下线（已下架）内容，是所有编辑与删除的唯一落点。一张内容同一时刻只存在于其中一张表，两表之间靠 `uid` 认同一份内容、靠 `slug` 跨表判占用（见 §2.6）。
- **线索实体**：`inquiries` / `cooperation` / `contact_messages` 来自前台表单，统一含 `status` 状态机，可关联 `handled_by`（运营）。
- **配置实体**：`site_settings`（KV）、`menus`（树）、`roles`（RBAC）。

| 表 | 关键字段 | 说明 |

| `pages` | slug(唯一), title, meta_*, hero_image, status, content_json(JSONB), draft_json(JSONB), published_at | 可编辑单页；`content_json` 线上正式版本、`draft_json` 管理端草稿版本，均为区块化结构 `{ blocks:[...] }`（见 §5.1）。迁移 `002_page_blocks.sql` 新增 `draft_json` 并写入 home/about/products/news/contact 种子；迁移 `003_list_blocks.sql` 在 products/news 页插入 `product-grid`/`news-feed`/`poster-grid`/`cta-banner` 区块 |
| `article_categories` | name, slug(唯一), description, sort | 资讯分类；`slug` 由服务端在创建时生成（`ac-` + 6 位 `[a-z0-9]`）后冻结、无写入路径，管理端只读回显；管理端列表回传跨两表的 `ref_count`，被引用时删除被拒 |
| `articles` | uid, slug, title, cover_image, body(HTML), category_id, tags(JSONB), status, published_at, view_count, updated_by | **线上表**：只放已上线行，`status` 恒为 1（`CHECK (status = 1)`）、内容列只读；`uid` 为跨表内容身份；`slug` 由服务端在建草稿时生成（`a-` + 6 位）后冻结，发布时随行搬进本表、改名也不变；`published_at` 首次发布写入、再发布不覆盖 |

| `product_categories` | name, slug, parent_id(自引用), sort | 产品分类（多级）；`slug` 由服务端在创建时生成（`pc-` + 6 位 `[a-z0-9]`）后冻结，同时是官网分类筛选的取值；`ref_count` 跨 `products` + `product_drafts` 统计，删除保护同口径 |
| `products` | uid, slug, name, category_id, series, cover_image, gallery(JSONB), summary, description, specs(JSONB), highlights(JSONB), price_text, buy_link, status, sort, published_at, updated_by | **线上表**：只放正在上架的产品，`status` 恒为 1（`CHECK (status = 1)`）。gallery/specs/highlights 均为 JSONB 数组。唯一可写的非内容列是 `sort`（`POST /products/:id/sort`）；`slug` 由服务端在建草稿时生成（`p-` + 6 位）后冻结、上架时随行搬进本表；`uid` 是内容身份，`published_at` 首次上架写入、再上架不覆盖 |
| `product_drafts` | uid, slug, name, category_id, series, cover_image, gallery, summary, description, specs, highlights, price_text, buy_link, state, sort, published_at, updated_by | **未上架表**：`state IN (0,2)` = 草稿 / 已下架；内容已上架时本表无行（故「是否存在未发布改动」这一概念在产品域不存在）；编辑、删除、发布、下架的唯一落点（都不碰 `slug`），`sort` 与 `published_at` 随行搬运 |
| `banners` | title, image_url, link_url, position, sort, status, start_at, end_at | 广告位，按 position 区分页面 |
| `faqs` | question, answer, category, sort, status | 售后/保修/退换 FAQ |
| `media` | filename, original_name, mime_type, size, bucket, object_key, url, category | 媒体库，记录云端对象键与访问 URL。支持改名（`original_name`）/归类（`category`）但**不改动访问 `url`**（避免已发布内容失效）；删除前按 `object_key` 跨 `pages`/`products`/`articles`/`article_drafts`/`product_drafts`/`banners` 扫描引用，被引用时拒绝删除（两张未上线表也在清单内：只被草稿引用的素材删掉一样会成死链） |

### 2.5 审计
| 表 | 关键字段 | 说明 |
|---|---|---|
| `audit_logs` | user_id, action, entity_type, entity_id, diff(JSONB), ip | 操作留痕（`create/update/delete/publish/unpublish/sort`）。资讯与产品两类实体的 `entity_id` 写 **`uid`** 而不是行 id（行 id 会随搬运消失，`uid` 才是「同一条内容」），因此一条内容的「建 → 改 → 上架 → 调排序 → 下架 → 再改 → 再上架」能按同一 `uid` 串成不断线的时间线；`entity_type` 恒为 `article` / `product`（不出现 `*_draft`）。`diff` 形态 `{fields, from, to}`，`fields` 只收**值真的变了**的列，`articles.body` 与 `products.description` 只记 `{length, summary}` 而不整份入库。其它实体的记录仍是旧形态（`entity_id` = 行 id、`diff` 为空） |

### 2.6 内容双表：放置、搬运与三态判据

资讯与产品各有一对表（`articles`/`article_drafts`、`products`/`product_drafts`），形态同构、表与状态文案各自独立。要点：

- **放置规则**：一条内容同一时刻只存在于一张表。正在对外可见 → 线上表；其余（从没上过线、或曾上线已被撤下）→ 未上线表。
- **三态判据 = 在哪张表 + 未上线表的 `state`**，不看线上表的 `status`（它恒为 1，只作已上线标记）：

  | 判据 | 资讯称谓 | 产品称谓 |
  |---|---|---|
  | 线上表有行 | 已上线 | 已上架 |
  | 未上线表 `state=0` | 草稿 | 草稿 |
  | 未上线表 `state=2` | 已下线 | 已下架 |

  文案由服务端常量单点给出（`ARTICLE_STATE_TEXT` / `PRODUCT_STATE_TEXT`），列表行的 `state_text` 与接口错误提示都引用它；前端不另维护一份称谓映射。
- **四个动作的落点**：新建/编辑/删除只作用于未上线表；**发布**与**下架**都是同一事务内的整行搬运（`INSERT … SELECT` + `DELETE`），搬运清单显式写出内容列 + `uid` + `published_at` + `created_*`（产品侧再带 `sort`），`uid` MUST NOT 走列默认值重新生成，否则审计历史断线。
- **线上内容只读**：已上线/已上架行没有编辑与删除入口，也没有 `PATCH` 线上行的端点；想改内容必须先下架（撤下 → 编辑 → 再发布）。产品侧唯一的例外是列表顺序：`POST /products/:id/sort` 只写 `sort` 与 `updated_by`，内容列、`status` 与 `published_at` 一律不动。
- **`slug` 由服务端在创建落库时生成、一经生成即冻结**：内容为「`p-`/`a-` + 6 位 `[a-z0-9]`」、分类为「`pc-`/`ac-` + 6 位」（`node:crypto` 的 `randomInt` 等概率取样，不是时间戳或自增号）。生成时跨两表查占用（`SELECT 'online' … UNION ALL SELECT 'draft' …`，分类只查本表），占用则重取、上限 5 次；此后任何写入路径都不接收也不改写标识——编辑、发布、下架、调排序都原样带着走，跨表搬运时随行过去；外部提交的 `slug` 被请求校验静默丢弃（既不报错也不生效）。两张表各留 `UNIQUE (slug)` 与 `UNIQUE (uid)` 兜并发，PG 的 23505 转 409 而不是 500。
- **存量手工标识不迁移**：既有行的 `slug` 保持原值继续可用，老地址不失效、不重排。因此搬运路径仍要判冲突：发布/下架时若整行搬过去会和另一张表的存量手工标识同名，仍按 409 拒绝，并区分「撞线上」与「撞未上线」给不同中文提示。
- **随搬运保留、不因换表重置**：`published_at`（首次上/上架时间，之后每次再发布只延续不覆盖）、`sort`（产品）、`view_count`（资讯）。
- **官网与公开接口只读线上表**，MUST NOT join 或 union 未上线表——「草稿不外泄」交给表结构，而不是每条 SQL 的过滤条件。

## 3. 状态枚举约定

| 字段 | 取值 | 含义 |
|---|---|---|
| users.status | 1 / 0 | 启用 / 禁用 |
| articles.status | 1 | 恒 1，只作「已上线」标记；`CHECK (status = 1)`，草稿与已下线不写本表（见 `article_drafts.state`） |
| article_drafts.state | 0 / 2 | 草稿 / 已下线；`CHECK (state IN (0,2))`，已上线不写本表故无 1 |
| products.status | 1 | 恒 1，只作「已上架」标记；`CHECK (status = 1)`，草稿与已下架不写本表（见 `product_drafts.state`） |
| product_drafts.state | 0 / 2 | 草稿 / 已下架；`CHECK (state IN (0,2))`，已上架不写本表故无 1 |
| pages.status | 1 / 0 | 已发布 / 已下线（`pages` 走 `content_json`/`draft_json` 双列范式，与内容双表不同构） |
| banners/faqs/menus.status | 1 / 0 | 显示 / 隐藏 |
| inquiries/cooperation/contact_messages.status | 0 / 1 / 2 / 3 | 新线索 / 跟进中 / 已成交 / 无效 |
| subscriptions.status | 1 / 0 | 订阅 / 取消 |

> 内容三态（草稿 / 已上线·已上架 / 已下线·已下架）的判据是「在哪张表 + `state`」，不是任何单个列的取值；见 §2.6。

## 5. JSONB 字段结构约定

- **products.specs**：`[{"label":"容量","value":"20TB"}, ...]` —— `{label,value}` **有序数组**（≤20 项，行序即官网展示序），`label` 必填；`{}` 对象形态与非数组在写入前被拒，读侧把历史 `{}` 归一为 `[]`
- **products.highlights**：`["原厂直供","稳定供应", ...]`（≤8 条字符串）
- **products.gallery**：`["/website/img/prod/cube.png", "/uploads/2026/10/xxx.webp"]`（≤8 项**可直接渲染的图片地址**，站内路径或素材 URL，不是 object_key 数组）
- **articles.tags**：`["贸易合规","市场洞察"]`
- **audit_logs.diff**：`{"fields":["name","price_text"],"from":{"name":"…","price_text":null},"to":{…}}`；正文类长字段存 `{"length":34,"summary":"…"}`
- **pages.content_json / draft_json**：整页区块化结构，见下方 §5.1 区块规范
- **roles.permissions**：`["content:read","content:write"]` 或 `["*"]`

### 5.1 pages 区块（blocks）规范

页面内容 = 有序区块列表，`content_json` 与 `draft_json` 结构一致：

```jsonc
{
  "blocks": [
    {
      "id": "home-hero",        // 区块实例 id（编辑器新增时前端 genBlockId 生成，type+随机短串）
      "type": "hero",            // 区块类型，对应前端 sectionRegistry
      "visible": true,           // 显隐开关（false 时前台/预览跳过渲染）
      "props": { /* 各类型专属内容数据：文案/图片/列表项 */ }  // 仅内容，不含样式结构
    }
  ]
}
```

- **草稿/线上双版本 + 发布覆盖的数据流**：
  - 管理端编辑器「保存草稿」→ `PUT /pages/:id/draft` 仅写 `draft_json`（经 `deepSanitize` 递归清洗），`content_json` 不变，官网前台不受影响。
  - 「发布」→ `POST /pages/:id/publish` 执行 `content_json = draft_json, status = 1, published_at = COALESCE(published_at, NOW())`；草稿为空（`draft_json.blocks` 非数组）时后端拒绝发布，避免覆盖成空内容。
  - 「放弃草稿」→ `DELETE /pages/:id/draft` 将 `draft_json` 复位为 `{}`，编辑器回落线上版本。
  - 「下线」→ `POST /pages/:id/unpublish` 置 `status=0`，公开接口按 `status=1` 过滤后不再返回该页。
  - 前台 `GET /public/pages/:slug` 只读 `status=1` 的 `content_json`，草稿不外泄。
- **has_unpublished_draft**（`GET /pages` 列表即时计算，不落库）：`(draft_json <> '{}'::jsonb AND draft_json IS DISTINCT FROM content_json)`，即草稿已结构化且与线上不同才提示「有未发布修改」。
- **迁移 `003_list_blocks.sql`（本轮已执行）**：不再重写整页，而是以 JSONB 切片在**指定区块（`page-hero`，第 1 块）之后插入**新区块——products 页插入 `product-grid`，news 页依次插入 `news-feed` → `poster-grid` → `cta-banner`。幂等条件：仅当 `content_json::text` 不含该区块 type（如 `NOT LIKE '%"product-grid"%'`）才插入，重复执行不产生重复区块、也不改动管理端已编辑的其余区块与顺序；当草稿也已结构化（`draft_json ? 'blocks'` 且不含该 type）时，`draft_json` 同步插入同一份新区块。
- **19 种区块类型**（type 与关键 props，与前端 `sectionRegistry.ts` 的 `defaultProps`、`pageDefaults.ts` 兜底、迁移种子三方一致）：

| type | 用途 | 关键 props |
|---|---|---|
| hero | 首页首屏 | eyebrow, title[], lede, cta1/cta2({text,link}), meta[{label,value}], image, imageAlt, floaterLeft/floaterRight({title,en}) |
| page-hero | 内页头图 | crumb[{text,link?}], title[], subtitle |
| intro-eco | 品牌/介绍 eco-grid | eyebrow, title[], desc, items[{h4,p}] |
| mvv | 使命与愿景 | eyebrow, title[], desc, theme(''/paper), cards[{tag,text}] |
| values | 品牌价值观 | eyebrow, title[], desc, items[{icon,title,en,text}] |
| timeline | 品牌历程/流程 | eyebrow, title[], desc, theme, items[{year,title,text}] |
| story | 深色品牌背景 | eyebrow, title[], paras[], pillars[{en,cn}], image, imageAlt, backers[{title,desc}], brandWall[{text,url?}] |
| cat-grid | 类别卡片（场景/政策） | eyebrow, title[], desc, theme, items[{num,icon,title,text,bullets[]}] |
| cap-flow | 产品特性四宫格（深色） | eyebrow, title[], items[{step,title,text,tags[]}] |

## 6. 索引与性能

- 所有 `slug` 字段唯一索引，作为公开路由标识（不可枚举性优于自增 ID）。内容与分类的 `slug` 由服务端在创建时生成、生成后冻结，生成时跨两表判占用（分类只查本表）；内容的 `slug` 与 `uid` 在线上表与未上线表**各自唯一**，并发下的同标识冲突由两表唯一约束兜住（23505 转 409）。
- `articles` / `products` 建立 `to_tsvector` GIN 索引支撑全站搜索。
- 列表查询按 `status + (published_at|sort)` 复合索引；外键列建索引。`inquiries(product_uid)` 建索引供线索列表按内容身份回查。
- 管理端内容列表把两张表 `UNION ALL` 后按**全序** `updated_at DESC NULLS LAST, origin, id DESC` 排序分页——只按 `updated_at` 排会让同一时刻的多行在翻页时重复或漏行。
- 大表（articles/products/audit_logs）按 `created_at` 分区可后期演进（单表千万级内无需）。

## 7. 安全与合规要点

- `password_hash` 存 `bcrypt(口令 SHA-256 摘要)`（cost=12）：前端只提交摘要，明文密码既不进接口也不落库。摘要即登录凭证，故接口必须走 HTTPS。
- `refresh_token` 仅存哈希，原始令牌签发后即弃。
- 富文本（articles.body / products.description / pages.content_json / faqs.answer）入库前须做 XSS 清洗（后端 `sanitize` + 站外图片剥除），官网按清洗后的内容直接渲染，不再二次过滤；产品描述的清洗链与资讯正文同规格，白名单不放宽（`style` 全剥、`class` 只在 `img` 上保留）。
- 已上线/已上架内容没有写入路径：管理端接口只从未上线表读、只往未上线表写，`uid` 与行 id 不符的写请求一律拒绝，避免「传错 id 静默改到别的内容」。
- `audit_logs` 对所有写操作留痕，满足 CMS-06 审核流需求。
- 个人信息（inquiries/contact 的 phone/email）按隐私政策最小化收集，并提供导出/删除接口（合规预留）。
