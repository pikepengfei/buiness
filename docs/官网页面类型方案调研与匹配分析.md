# 官网「后端编辑—发布—前端展示」页面类型方案调研与匹配分析

> 调研日期：2026-10-27
> 调研范围：互联网公开资料（Headless CMS、组件化页面构建器、低代码 Schema 渲染、可视化编辑、渲染/SEO 策略、区块编辑器选型）
> 目标：为「后台编辑不同类型官网页面并发布到前台」寻找成熟方案，总结技术效果，并对照 `z-buiness` 项目做匹配度分析，给出落地建议。

---

## 0. 背景与项目现状

`z-buiness` 当前已是一套**自研的区块化（block-based）页面构建器**，核心能力已在代码与文档中落地：

- **后端**：Node + TypeScript + Fastify + PostgreSQL + S3 兼容对象存储。
- **页面模型**：`pages` 表用 `content_json`（线上版）+ `draft_json`（草稿版）双版本，均为 `{ blocks:[{id,type,visible,props}] }`；`status` 控制上线/下线；`publish/unpublish` 原子切换。
- **区块类型**：`sectionRegistry.ts` 注册 19 种区块（hero / page-hero / intro-eco / mvv / values / timeline / story / cat-grid / cap-flow / poster-grid / feature-products / latest-news / product-grid / news-feed / pm-entry / faq-list / contact-form / cta-banner / rich-text），前端 `SectionRenderer` 按 `type → 组件` 映射渲染。
- **前台**：Vue3 + Vite + Pinia + Element Plus SPA，`views/website/*` 通过 `usePageBlocks(slug)` + `SectionRenderer` 由 CMS 区块驱动，目前为 **CSR（客户端渲染）**。
- **治理**：RBAC 权限点、审计日志 `audit_logs`、富文本 `sanitize-html` 清洗、公开只读 `/api/public/*` 与受保护接口分离均已实现。

本调研据此判断：项目与业界「组件化页面构建器」范式高度同构，重点差距在 **SEO 渲染策略** 与 **可视化/Live 预览体验**。

## 1. 业界主流方案分类

| 类别 | 代表 | 核心思路 | 适用 |
|---|---|---|---|
| ① 一体化 Headless CMS（SaaS/自托管） | Contentful、Sanity、Strapi、Payload、Directus、Umbraco Delivery API | 内容建模 + 自动 REST/GraphQL API + 自带管理后台 + 草稿/发布工作流 + 可视化编辑 | 不想自建 CMS、要快速上线 |
| ② 组件化页面构建器（Block/Slices/Bloks） | Storyblok bloks、Prismic slices、Builder.io、agent-cms | 页面 = 有序「区块」数组，内容为结构化 JSON，前端组件注册表映射渲染 | 营销站、需要区块复用 |
| ③ 自研低代码 Schema 渲染器 | 内部低代码平台（JSON Schema 驱动） | 页面 = JSON Schema（version + components[] + props），编辑器产出 Schema，渲染引擎消费 | 多端复用、强定制 |
| ④ 可视化编辑层（Visual Editing） | Storyblok/Sanity Presentation/Builder.io | 在结构化内容之上叠加可视化层（Live/Draft/Environment 预览） | 提升编辑体验 |

> 关键共识（headlesscms.info、Dre Dyson）：现代可视化编辑**不是自由式 WYSIWYG**（会产生不可控 HTML），而是**组件化区块**——编辑从开发者预定义的区块组装页面，内容保持结构化 JSON，可视化层只是渲染外壳。这要求一个**组件注册表（component registry）**作为 CMS 与前端之间的契约。

## 2. 实现方式与技术栈

| 维度 | ① 一体化 Headless CMS | ② 组件化页面构建器 | ③ 自研 Schema 渲染器 | ④ 可视化编辑层 |
|---|---|---|---|---|
| 内容模型 | GUI/代码定义 Collection+Field | 区块类型（blocks/slices） | JSON Schema（version + components） | 叠加在 ①②③ 之上 |
| 编辑体验 | 自带后台，开箱即用 | 区块拖拽/表单配置 | 表单/拖拽产出 Schema | Live/Draft 实时预览 |

| 前端渲染 | fetch API → 组件映射 | 区块数组 → 组件映射 | Schema → 渲染引擎 | 同左 + 编辑器叠加 |

| 渲染策略 | 取决于前端（多支持 SSG/SSR） | 取决于前端 | 取决于前端 | 取决于前端 |

## 3. 关键技术效果

### 3.1 内容与表现分离、区块复用
结构化 JSON 内容（非 HTML blob）让同一份内容多端复用（Web/iOS/Android/AMP/AI），且渲染可预测（每个 block type → 固定前端组件）。这是 composable content 的核心收益（Dre Dyson「Pattern 3」）。

### 3.2 草稿—发布版本化
成熟做法设 **Draft / Review / Published** 三态：草稿不进公开 API；Review 走带预览令牌的预览 API；Published 进公开 API。版本快照支持回滚（agent-cms、Payload `versions:{drafts:true}`）。项目采用的「草稿版/线上版双 JSON + 原子 publish」属同一范式，工程上更轻量。

### 3.3 渲染策略与 SEO（最关键的 SEO 决策）
| 策略 | 构建时 | 请求时 | SEO 安全性 | 最佳场景 |
|---|---|---|---|---|
| CSR | — | 空壳+JS 填充 | 差（Google 二次渲染延迟索引） | 后台/强交互 |
| SSR | 无 | 服务端取数渲染 | 优（完整 HTML） | 实时/个性化内容 |
| SSG | 构建期产出静态 HTML | CDN 直出 | 最佳（LCP 最优） | 博客/产品/营销页 |
| ISR | 静态 + 后台按需再生成 | 缓存在失效前为静态 | 优（速度+新鲜度兼顾） | 内容月更类目/列表 |

> 共识（OverTheTopSEO、SEOLOGY、CopeBusiness、Moburst）：headless 架构**剥夺了传统 CMS 自带的 SEO 脚手架**，必须显式实现 metadata、sitemap、canonical、结构化数据（Organization/Product/Article）。**纯 CSR 的营销站 SEO 风险最高**——这正是项目当前 SPA 形态的主要隐患。建议营销站用 SSG/ISR，仅动态页用 SSR。

### 3.4 可视化预览的工程成本
- **Live Preview**：编辑器实时渲染草稿，需 WebSocket/轮询或 CMS↔前端桥接（Storyblok iframe + bridge SDK、Sanity stega 注入），运维复杂（预览部署、令牌、CORS/CSP）。
- **Draft Preview**：保存草稿后开预览 URL 取未发布版，成本中等。
- **Environment Preview**：独立 staging，最可靠但最慢。

### 3.5 治理（Governance）
RBAC 角色粒度、审计日志、内容锁定、SSO 是 Headless CMS 评分卡中权重最高的项之一。项目已实现 RBAC 权限点 + `audit_logs` + 刷新令牌哈希，治理基线达标。

### 3.6 Schema 版本化与向前兼容
区块格式演进时，**全局一次性迁移风险高**（一行 bug 即污染生产页）。推荐做法（kuray.dev 实践）：每行页面带整数字段 `schemaVersion` + 索引；定义 `CURRENT_SCHEMA_VERSION` 常量；用「在内存中逐页迁移的阶梯函数」+ 可选字段（`.optional()`）实现**向后兼容读取**，老页面不重存也能渲染；`schemaVersion` 索引可查询「哪些页尚未升级」。这是项目下一步加固区块结构时应采纳的模式。

## 4. 与 z-buiness 项目匹配度分析

| 能力 | 项目现状 | 匹配度 | 说明 |
|---|---|---|---|
| 区块化内容模型（blocks + 19 类型 + sectionRegistry） | ✅ 已实现 | **高** | 与「组件化页面构建器」范式完全一致 |
| 草稿/发布双版本（draft_json/content_json + publish/unpublish） | ✅ 已实现 | **高** | 等同 Draft/Published 双态，原子切换 |
| 公开只读 API 分离（/api/public/*） | ✅ 已实现 | **高** | 与 Contentful/Sanity 公开交付 API 同构 |
| 组件注册表（sectionRegistry + SectionRenderer） | ✅ 已实现 | **高** | 即「CMS↔前端组件契约」，业界强调的关键基础设施 |
| RBAC + 审计日志 | ✅ 已实现 | **高** | 治理基线达标 |
| 富文本 XSS 清洗（sanitize-html） | ✅ 已实现 | **高** | 存储型 XSS 防护到位 |
| 媒体库 + 直传（S3 presign / local 降级） | ✅ 已实现 | **高** | 文件不走后端流量，符合最佳实践 |
| 可视化编辑 / 真·WYSIWYG | ⚠️ 部分 | **中** | 当前为 `formSchema` 驱动表单编辑（BlockForm），非拖拽式所见即所得 |
| 实时预览（Live Preview） | ⚠️ 部分 | **中** | 编辑器可加载 draft（by-slug），但缺少跨 iframe/实时同步预览 |
| 渲染策略与 SEO | ❌ 缺口 | **低** | 当前 SPA（CSR），营销站 SEO 风险；文档已标注 SSG/SSR 为后续演进 |
| 富文本编辑器体验（Notion-like） | ⚠️ 部分 | **中** | `rich-text` 区块存在，但非 Editor.js/BlockNote 级体验（且 Vue 生态，BlockNote 为 React） |
| 区块 Schema 版本化（schemaVersion + 在线迁移） | ❌ 缺口 | **中** | 有结构校验，但缺显式版本号与向前兼容迁移阶梯 |
| 多语言 / 国际化 | ⚠️ 预留 | **中** | Site store 预留双语 Slogan，未体系化 |

**结论**：项目与业界「自研 block-based page builder」方案**吻合度最高**，核心能力（建模、发布、注册表、治理、公开 API）均已具备。主要差距为 **①SEO 渲染策略（CSR）** 与 **②可视化/Live 预览**，其次为 Schema 版本化与富文本编辑体验。

## 5. 推荐落地路径（结合项目现状，按优先级）

### P0 — SEO 渲染升级（最高价值，直接对冲最大风险）
- 关键营销页（首页 / 产品 / 资讯 / 关于 / 联系）由 CSR 改为 **SSG 或 ISR**；仅动态/个性化内容保留 SSR。
- Vue 生态最顺滑路径：**Nuxt 3**（原生 SSR/SSG/ISR，与现有 Vue3 组件、`website.css`、`sectionRegistry` 可复用），或将现有 Vite SPA 增加**预渲染（prerender）** 产出静态 HTML 兜底爬虫。
- 同步补齐 SEO 脚手架：每页 `seo_title/seo_description/og_*`，`sitemap.xml` 由 `/api/public/*` 在构建期生成，Organization/Product/Article 结构化数据（项目文档 §7 已预留）。

### P1 — 预览能力增强
- 复用现有 `draft_json` + `pages/by-slug/:slug`，为编辑器增加「预览」路由/iframe：草稿实时渲染，发布即时生效（现有 no-cache + ETag 协商缓存已支持「发布即生效」）。

### P2 — 可视化编辑增强（可选）
- 在现有 `BlockForm` 上叠加**区块拖拽排序 + 即时预览**，向 Storyblok/Prismic 的「区块组装」体验靠拢；若需 Notion-like 富文本，评估 Vue 友好的 ProseMirror 封装（BlockNote 为 React，需桥接或选 Vue 等价方案）。

### P3 — 区块 Schema 版本化（加固）
- 给 `pages` 增加 `schemaVersion` 整型字段 + 索引；定义 `CURRENT_SCHEMA_VERSION`；区块校验对新增字段用 `.optional()` 实现向后兼容读取；提供在线迁移函数（参考 kuray.dev 阶梯迁移），避免格式演进破坏老页面。

### 决策建议
**不建议替换整套 CMS**（如迁 Sanity/Contentful）。项目自建方案已覆盖 80%+ 核心能力，迁移成本高、且会丢失已落地的区块体系与 RBAC/审计。优先补 **P0（SEO 渲染）** 与 **P1（预览）**，即可达到业界营销站主流水平。
