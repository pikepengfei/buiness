# 组件库堆叠式装修 · 方案选型与实施设计

> 版本：v1.0 ｜ 日期：2026-11-05 ｜ 范围：buinessweb（官网前台 + /admin 管理端）+ backend（Fastify + PostgreSQL）
> 前置阅读：`02-官网低代码装修平台设计与实施文档.md`（现行区块体系）、`docs/页面编辑-草稿发布-显示-实现方案.md`（区块版本化）
> 本文只回答一个问题：**「组件库 → 预制组件 → 管理端拼接 → 官网显示」这条路该怎么走**，并给出可执行的实施设计。

## 1. 诉求还原

用户描述拆成 5 个能力维度，逐项对照现状打分（●=已具备 / ◐=部分 / ○=没有）：

| # | 能力维度 | 含义 | 现状 | 证据 |
|---|---|---|---|---|
| C1 | 物料化组件库 | 可浏览、可检索、可复用的组件清单 | ◐ | 4 个分组 19 种区块，仅在「新增区块」弹窗里点选，无独立物料面板：`sectionRegistry.ts:387` |
| C2 | 组件拼接（嵌套） | 容器组件内装载子组件，树形组合 | ○ | `Block` 只有 `{id,type,visible,props}`，无 `children`/`slots`：`website/blocks.ts:10-15` |
| C3 | 画布拖拽 | 拖入、换位、层级缩进 | ○ | 编辑器只有上下移按钮；`package.json` 无任何拖拽类依赖（全仓无 sortable/draggable） |
| C4 | 预制与复用 | 跨页复制、模板库、一键铺版 | ○ | 已提案未落地：`openspec/changes/decoration-editor-toolkit/tasks.md`（0/50） |
| C5 | 生效链路 | 草稿→发布→官网渲染 | ● | 双版本 + 原子发布 + ETag 协商缓存 + 递归 `deepSanitize`，见 02 文档 §4 |

**判定**：现有实现是「**区块级 CMS 拼装**」，属内容级低代码（页面 = 一维区块列表，版式焊死在 `website.css`）。与用户要的「组件堆叠」差的正是 C2+C3+C4 三项，而 C1 只是形态问题（有没有物料面板）、C5 完全不用动。

## 2. 仓库内既有的三套方案（先看自家再谈业界）

### 2.1 已落地：注册表驱动的扁平区块体系
- **模型**：`{ blocks: [{ id, type, visible, props }] }`，`content_json`（线上）/ `draft_json`（草稿）同构。
- **注册表**：`SECTION_REGISTRY[type] = { label, group, component(markRaw), defaultProps(), formSchema }`；`SECTION_GROUPS = ['头部与首屏','图文内容','数据驱动','转化组件']`。
- **表单**：`FieldKind` 10 种（`text/textarea/html/number/image/select/lines/link/object/list`），`BlockForm.vue` 对 `object`/`list` **已递归复用**——这是现成可借的递归渲染范式。
- **渲染**：`SectionRenderer.vue:14-16` 过滤 `visible===false` 与未注册 `type`，`:21-27` 动态分发；**顺序遍历，不递归**。
- **容错**：`parseBlocks` 每次读取跑 `migrateBlock`（`CURRENT_BLOCK_SCHEMA_VERSION = 1`），老 JSON 不重存也能渲染。
- **性质**：组件是「整块版式」，19 个即 19 种版式，颗粒度粗，**拼接发生在页面层（区块顺序），不在组件层**。

### 2.2 已提案未实现：`decoration-editor-toolkit`（装修工具包）
拖拽排序（原生 HTML5，零依赖）、区块复制、跨页复制、`block_templates` 模板库（迁移 009）、`pageDefaults` 作为模板源、多选批量、插入时与 `defaultProps` 浅合并并对已下线 type 禁用。**提案已明确「无破坏性变更：区块数据模型不变」**——也就是说它解决 C1 形态 + C3 排序 + C4，但**不解决 C2 嵌套**。

### 2.3 相关既有约束（改造必须戴着跳舞）
- `site-runtime-link-integrity`（C1 change）：**取消前台内置内容回落**，装修页未发布 / blocks 空 / slug 不存在 → 品牌化 404；`pageDefaults.ts` 降级为「编辑器默认模板数据源」。落地后「靠 `usePageBlocks` 兜底显示」这条安全网不复存在。
- `page-publication-approval`：发布内容来源改为**已批准快照**（`page_versions.blocks jsonb`），编辑使批准失效、职责分离、回滚到任意历史版本。
- 后端校验：`content.ts:27-34` 的 `blocksSchema` 是**扁平 zod 对象 + `.max(200)`**，且注释写明「具体 type 与 props 由前端注册表定义，后端不校验」——嵌套模型必须改这里。
  > 现状（2026-11-06）：已改递归并迁到 `backend/src/blocks.ts`（`z.lazy` 节点树 + `BLOCK_LIMITS` + `blockLimitIssues` 深度/总数复核 + 路径化错误消息），「不校验」的分工仍保留在 **props 内容**层面，结构骨架与上限已在服务端强制。

## 3. 业界路线对比

| 路线 | 做法 | 满足 C1-C4 | 改造面 | 关键风险 | 结论 |
|---|---|---|---|---|---|
| **R1 只做工具包** | 落地 2.2 提案，仍是扁平列表 | C1◐ C2○ C3● C4● | 小（前端 + 1 张表） | 用户说的「拼接」体验仍然拿不到 | 不够 |
| **R2 三层组件模型 + 递归容器**（自研增强） | 原子件/区块/容器三层，`children` 树 + 递归渲染 + 物料面板 + 画布拖拽 + 树形模板 | C1● C2● C3● C4● | 中（见 §4 分期） | 递归渲染与校验要新写；版式仍需人工维护 CSS 栅格 | **推荐** |
| **R3 GrapesJS 作画布内核** | 引入框架无关的 HTML 层编辑器，导出 HTML 存库 | C1● C2● C3●● C4● | 大（渲染改回 HTML，区块组件体系作废） | 产物是 HTML 而非结构化 blocks → 与双版本/审核快照/数据驱动区块/SEO meta 全线冲突；官网「固定版式」失守 | 不建议 |
| **R4 TinyEngine（华为 OpenTiny）** | Vue3 低代码引擎，schema = componentsTree，物料需 UMD 注册 | C1● C2● C3●● C4● | 极大（设计器独立工程 + 需自建后端平台） | 与 `pages.content_json` 不同构（无损导入导出做不到）；`faq-list` 这类「组件内自拉 API」要重写成引擎数据源；社区更新节奏已放缓（gitee 仓库列表显示最近更新约半年前，2025-11 口径） | 不建议 |
| **R5 阿里 LowCodeEngine** | 企业级低代码引擎 + 物料协议 | C1● C2● C3●● C4● | 极大 | 设计器与**出码均为 React**，官网是 Vue3 SPA，要么双栈维护要么加一层 schema→Vue 渲染器；工程门槛（node 版本、UMD 调试）与我们的 Vite 单仓不合 | 不建议 |
| **R6 JSON-Schema 驱动（amis/formily 式）或出码 .vue** | 声明式配置渲染 / 低代码生成源码提交 | C2◐ | 中 | amis/formily 面向**中后台表单页**，不是营销内容页；出码路线等于「装修产物进 git」，与 CMS 草稿-发布模型相互抵消 | 不匹配 |

> 否决 R3/R4/R5 的共同理由，一句话：**它们的价值在「任意画布 + 出码/自建平台」，我们的需求是「固定版式下的内容拼装 + 审核发布」**。为拿到 C3 的拖拽体验而废掉 C5 已跑通的草稿/发布/审核/缓存链路，是净损失。业界重型引擎适合「多站点、多应用、需要出码交付」的平台团队，不适合单官网 CMS。

## 4. 推荐方案 R2 详细设计

> **落地状态（2026-11-06）**：R2 的 **P1 已由 `openspec/changes/home-decoration-components/` 启动并落地下单批范围**，与本文设想有三处口径差异，以该 change 的 design.md 决策为准：
> ① 首期不引入 grid/split/band 三个容器，改成「**模块直接装载基础元素**」的一级嵌套（`accepts: ['atom']`，容器套容器禁用），把递归的 UX 风险压到最小；
> ② 原子件命名从 `a-*` 改为 **`ui-*`**（`ui-text`/`ui-heading`/`ui-image`/`ui-button`），实现落在 `src/components/ui/`，与模块内部用的是同一份组件（不再有「装修专用壳组件」）；
> ③ P2 的画布拖拽暂未启动（D8：本期用上下移 + 路径选中，不引入 sortablejs），组件库面板已按 P2 的常驻形态落地。
> 本节以下的分层图、分期表保留原设计口径，作为 P1 剩余部分与 P2/P3 的参照。

### 4.1 组件分层（回答「组件库里有什么」）

```
容器 Container  ── 只负责布局，可装载子节点，自身不含业务语义
  ├─ grid      2/3/4 列自适应（列数由 props.columns 决定，移动端按断点降列）
  ├─ split     左文右图 / 左图右文两栏
  ├─ stack     纵向堆叠 + 间距档位
  ├─ tabs      内容分组切换（子节点按 title 分页签）
  └─ band      整段背景带（theme: paper/dark/brand）
区块 Section    ── 现有 19 种，语义不变，成为「预制件」，仍可含 children（如 hero 下追加 grid）
原子件 Atom     ── 新增最小可复用单元，供容器里自由拼
  ├─ a-headline（eyebrow/title/desc）  ├─ a-text（html）      ├─ a-image（src/alt/radius）
  ├─ a-button（link/ghost/size）       ├─ a-tag 组            ├─ a-kpi（num+label）
  └─ a-card（图+标题+文+链接，grid 的默认填充物）
组合 Composite  ── 「多节点片段」模板：一段 grid + 3 个 a-card 存成模板，一键插入
```

**注册表升级**（`sectionRegistry.ts` → 拆为 `componentRegistry.ts`，保留 `SECTION_REGISTRY` 别名不破坏现有 import）：

```ts
interface ComponentMeta {
  label: string;
  group: string;                 // '容器' | '头部与首屏' | ... | '原子件'
  layer: 'container' | 'section' | 'atom';
  component: any;
  defaultProps: () => Record<string, any>;
  formSchema: FieldSchema[];
  // ↓ 拼接约束（新增，是低代码体验的关键）
  accepts?: string[];            // 容器可装载的类型白名单；'*' 表示任意
  allowedIn?: string[];          // 本组件可被放进哪些父容器
  maxChildren?: number;
  isContainer?: boolean;
  variants?: { key: string; label: string; patch: Record<string, any> }[]; // 同一组件的预制变体
}
```

### 4.2 数据模型 v2（最小破坏）

```ts
export interface Block {
  id: string;
  type: string;
  visible: boolean;
  props: Record<string, any>;
  children?: Block[];   // v2 新增：仅容器/允许装载的区块使用；缺省 = 无子节点
}
export const CURRENT_BLOCK_SCHEMA_VERSION = 2;
```

设计取舍（明确写清为什么这样切）：
- **只做单一 `children` 序列，不做具名多插槽 `slots`**。多插槽会让校验、拖拽插入点、模板合并三处都翻倍复杂，而 `grid/split/tabs` 三个容器已覆盖官网全部版式需求；真有需求再加 `props.slot` 标记，属可增量演进。
- **`children` 缺省即不存在**，v1 扁平页面在 v2 渲染器下**逐字节不变**，`migrateBlock` 只需 `v1→v2 = 补 children 字段并剔除内部版本标记`，不需要重写任何存量页。
- **反向兼容**：v2 树被 v1 渲染器读取时，`children` 被忽略 → 容器渲染成空壳。**因此上线顺序必须是「先部署前端递归渲染，再允许编辑器产出 v2」**，写进发布 checklist。
- **约束上限**：深度 ≤ 4（超过 4 层的营销页必然失控）、单页总节点 ≤ 400、单容器 `children` ≤ 50。树非图，无需循环检测。

### 4.3 渲染层

- `SectionRenderer.vue` 改为递归：容器组件自己渲染 `children`（通过 `provide` 向下传 `preview` 与深度），或统一由 Renderer 递归 + 容器只出栅格壳。**选定：Renderer 递归**，容器只负责栅格 DOM 与列数换算，逻辑集中、好测。
- 未知 `type` 与 `visible===false` 的过滤沿用 `SectionRenderer.vue:14-16`，递归后每层都要过（含子层）。
- 新增栅格类必须落进 `assets/website.css`，并**沿用现有 4 个断点** `1100/860/640/480`（`website.css:855,876,881,974,1012`），列数在这些断点降为 2/1；容器不做像素定位。
- `preview` 模式（编辑器右栏 `transform` 缩放）对深层嵌套的开销做一次性验证：单页 200+ 节点时右栏预览改为**虚拟滚动或延迟渲染**（P2 再定，不预先优化）。

### 4.4 编辑器（低代码体验的落点）

| 区域 | 现状 | 目标 |
|---|---|---|
| 左：物料面板 | 弹窗点选 4 分组 | 常驻面板，按 `layer`/`group` 折叠 + 搜索 + 图标缩略；容器/区块/原子件三段 |
| 中：画布 | 线性区块列表 | 树形画布：容器可展开、hover 插入线、拖拽换位、选中层级面包屑（`首页 › 首屏 › grid(3) › a-card`）；保留上下移按钮作为拖拽的等价手段（无障碍） |
| 右：属性 | `BlockForm` 按 formSchema | 不变；新增 `kind: 'node-list'`（容器子节点内联排序，给不用画布的场景兜底）；`variants` 渲染成顶部切换条 |
| 顶栏 | 存草稿/发布/下线/放弃草稿/页面信息 | 增加撤销重做（内存 history 栈，≤50 步，**不入草稿、不落库**）、结构校验提示（超出 `accepts`/深度时禁止保存并定位） |
| 模板 | 无 | `block_templates` 的 `payload` 从「单区块」放宽为「节点树」；插入时**整树重生成 id**（`genBlockId`）并对每类 `defaultProps` 浅合并；`pageDefaults` 五套默认页注册为「整页组合模板」，新建页面可按类型一键铺版 |

拖拽实现二选一，**P2 开始前定**：
- 原生 HTML5 DnD：零依赖（与 toolkit 提案一致），但跨容器嵌套的插入点计算与移动端体验要自己写。
- `sortablejs`（~10KB，MIT）：嵌套排序/跨容器搬运成熟，代价是新增一个依赖且需与 Vue 的响应式列表同步（`onEnd` 里改数据，不让库直接搬 DOM）。
> 倾向 sortablejs：嵌套树拖拽是这类功能里最容易写出 bug 的地方，自研成本高于一个 10KB 依赖。此项需你点头。

### 4.5 后端

- `blocksSchema` 改递归（`z.lazy(() => ...)`）+ `maxDepth`/`maxNodes` 校验，`props` 仍不校验内容（保持「后端不维护类型清单」的既有分工）；错误消息带路径（如 `blocks.2.children.0.type`），沿用 400/1001。**已落地**：实现见 `backend/src/blocks.ts`，上限取 `{ maxDepth: 4, maxNodes: 400, maxChildren: 50, topBlocks: 200 }`，与前端 `src/website/blocks.ts` 的 `BLOCK_LIMITS` 同值。
- `deepSanitize` 已递归遍历对象与数组，`children` 自动被覆盖，无需改动（需在单测里断言）。**已断言**：后端无测试运行器，断言固化在 `backend/scripts/verify-blocks.ts`（`npx tsx` 直接跑），另在 `PUT /pages/:id/draft` 实测「`<p onerror=…>` → `<p>`、`<script>…</script>文字` → `文字」」。
- 新增 `009_block_templates.sql`（toolkit 提案既有）：`payload JSONB` 存节点树 + `kind`（single|tree）+ 创建人。**尚未启动**，与本期无耦合。
- `page_versions.blocks` 是整份 JSONB 快照，树形结构**无需迁移**；审核状态重置规则沿用（结构变更 = 内容变更）。
- 审计、发布原子切换、`/public/pages/:slug` 的 `no-cache` + ETag 全部不变。
- 数据侧唯一的本次动作是 `013_home_module_seed.sql`（+ 成对反向）：无 DDL，只在 home 页内容仍等于内置默认 9 模块划分时把 `pages.schema_version` 标为 2，运营已编辑则跳过并 `RAISE NOTICE`。

### 4.6 分期与工作量（人日为粗估，含自测）

### 4.7 明确不做（避免又滑回像素级自由画布）

自由绝对定位、任意内联样式/CSS 编辑器、多断点分别装修、装修产物出码进 git、组件级 JS 逻辑编排、第三方物料市场。
理由：官网原始需求第 2 条就是「**固定宽度与结构，管理端只编辑内容**」；版式一致性由 `website.css` 保证，放开样式编辑等于把审核流变成视觉走查地狱。移动端适配一律走既有 4 断点自动降列，不给运营单独配移动端。

### 4.8 与既有 3 个未落地 change 的先后

1. `decoration-editor-toolkit`（本方案 P0，被吸收）
2. `site-runtime-link-integrity`（C1：取消内置回落 → 未发布即 404）**必须在 P1 前落地或同时落地**，否则「新容器版式没发布」时会退到 `pageDefaults` 旧扁平内容，出现「编辑的和看到的不是一回事」的误导。
3. `page-publication-approval`（审核+快照）建议排在 P2 之后：审核按钮语义在拖拽画布稳定后再改，返工面最小。

### 4.9 文档回写点名（吸取「文档失同步」教训）

本方案落地时，以下每一份都要**在任务清单里逐文件点名**，不能只改 service-design：
`docs/数据结构文档.md`（Block v2 树 + 深度/数量上限）、`docs/接口文档.md`（递归 blocksSchema 与错误路径、`/block-templates`）、`docs/后端执行文档.md`、`docs/前端执行文档.md`、`docs/service-design/02-…`（§3 区块体系需加「容器/原子件」两层并修订「结构固定」表述）、`openspec/config.yaml`（内容模型那条描述）、新 change 目录 `openspec/changes/component-composition-decoration/`。
